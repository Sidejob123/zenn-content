Dify でワークフローを設計していて、ある Workflow Tool の呼び出しが遅いことは分かっていたが、どのステップで遅いのかを特定するのに余計な時間がかかっていた。Tool の呼び出し全体の時間は外部トレース（Langfuse）で見えていたが、内部は見えない。「Tool の中に入ってログを追う」という手順が毎回必要だった。v1.19.0 のネストトレースはこの問題に正面から答えている。

## ネストトレースで変わること：「Tool スパンを開く」という観点

今まで外部トレースに出ていた情報：
- 外側のワークフローのステップ（ノードごとの実行時間）
- 呼び出した Workflow Tool のスパン（通った/失敗した/実行時間）

v1.19.0 以降で追加される情報：
- Workflow Tool の呼び出しスパンの下に、内部ステップが階層で並ぶ
- 各内部ステップの LLM コール（プロンプト・レスポンス・トークン数・レイテンシ）
- 繰り返し呼ばれた場合の各呼び出しの履歴（1回目と2回目で何が違ったか）

これで「Tool の中のどのステップが遅い」「何回呼ばれているか」「LLM のレスポンスがおかしいのはプロンプトの問題か」を、外部トレースの画面だけで確認できるようになる。

企業内で Dify を使っていると、外側の「お客様向けチャットボット」ワークフローが、社内データを取ってくる「データ取得Tool」「要約Tool」「フォーマットTool」をそれぞれ呼び出す、という構成になることがある。今まで「データ取得Toolが10秒かかっている」は分かっても、「10秒のうち、API呼び出しが8秒で、LLM処理が2秒」という内訳は見えなかった。

## 設計への影響1：Workflow Tool の粒度を見直す機会になる

ネストトレースが取れるようになったことで、「Tool の中で一番時間がかかっている処理」が可視化される。これは設計の問題を炙り出すことにもなる。

たとえば、「データ取得→整形→要約」をひとつの Tool にまとめていた場合、ネストトレースを見て「要約のLLMコールが全体の70%を占めている」ことが分かれば、「要約だけ別のTool・別のモデルに切り出す」という設計判断をデータで裏づけできる。

逆に、粒度を細かくしすぎている Tool があると、ネストトレースに大量のスパンが並んで読みにくくなる。ネストトレースを導入したら、まず「スパンが多すぎてツリーが深すぎる Tool はないか」を確認すると良い。

Tool の命名も見直しの対象になる。外部トレースに出る Tool のスパン名は、ワークフロー内で設定した Tool の名前になる。「tool_1」「get_data」のような名前だと、ネストトレースを見たときに何のToolなのかが分からない。ネストトレースを活かすためには、Tool の名前を「何をするToolか」が分かる形に揃えておく必要がある。

## 設計への影響2：Workflow Tool のパッケージ移植が楽になる

v1.19.0 で `.ifpkg`（format v2）に Workflow Tools の定義が含まれるようになった。これは「環境間移行の設計」に影響する。

今まで：
- App をエクスポート → 別環境でインポート → Workflow Tools が含まれないので再作成が必要
- Tool の更新 → 移行先で手動で同じ変更を適用

v1.19.0 以降：
- App をエクスポート → `.ifpkg` に Tool の定義が含まれる
- インポート先で既存 Tool があれば再利用、なければ自動作成

これで「開発環境で作った App＋Workflow Tool のセット」を「本番環境に持っていく」手順が、エクスポート→インポートで完結するようになった。

ただし、注意点がある。すべてのエクスポートが format v2 になるため、**インポート先が 1.19.0 以上でないと受け付けない**。複数の Dify 環境を使っている場合（開発・ステージング・本番）は、先にすべての環境を 1.19.0 にアップグレードしてから、エクスポート・インポートを行う必要がある。

「開発を 1.19.0 に上げた後、まだ本番が 1.18.x で、開発からエクスポートしたパッケージを本番に入れようとして弾かれた」というケースは十分に起きうる。移行の順序を先に決めておく。

## 設計への影響3：difyctl による Skills の CI/CD 組み込み

v1.19.0 で `difyctl` に Skills 管理の6コマンドが追加されたことで、「Skill の変更を Git ベースのフローで管理する」ことが現実的になった。

具体的なフロー：
1. `difyctl export skill` でドラフトを ZIP で取り出す
2. Git にコミット・レビュー
3. `difyctl import skill --files` でドラフトを更新
4. `difyctl publish skill` で新バージョンを公開

これはまだ「CI/CDに組み込める要素が揃った」段階であり、実際に GitHub Actions のパイプラインに組み込むには、`difyctl` の認証（アカウント caller 権限）とトークン管理の設計が別途必要になる。今後試してみる予定。

## アップグレード前に確認しておくこと（4点）

v1.19.0 へのアップグレードで踏む可能性があるポイントを4点まとめる。

**1. Docker Compose のバージョン確認**

```bash
docker compose version
```

2.35.0 未満の場合は先にアップグレード。これが最初に確認すべきこと。

**2. ローリングデプロイの場合はトレースキューの移行**

新旧 worker が混在する期間は `ops_trace_v2` と `ops_trace` の両方を処理できるよう設定が必要。古いキューのワーカーは、溜まっているタスクが空になってから停止する。

**3. インポート先の環境を先に揃える**

`v2` パッケージを受け取れるのは 1.19.0 以上のみ。複数環境は同時にアップグレードするか、移行順序を明確にしておく。

**4. 環境ファイルの整理**

`docker/envs/core-services/api-worker.env` が新しくなった。`shared.env` は引き続き使えるが、カスタマイズの置き場所が変わっているため、既存の設定との重複・競合を確認する。

## この検証の限界

今回の整理は公式リリースノートの範囲に基づいている。ネストトレースの実際の見え方・設計への影響は、実際に Langfuse などの外部トレースに繋いで確認してみないと分からない部分が多い。

Workflow Tool の粒度や命名に関する話は、筆者の環境での判断であって、すべての Dify 環境に当てはまるわけではない。
