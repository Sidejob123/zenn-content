## TL;DR

並列実行はスループットが約8倍上がった。でも全部のフローを並列にしたら順序依存のバグが出た。有効にする前に「順序依存がないか」「スロットリングが起きないか」「エラーのデバッグができるか」の3点を確認するようにした。

## はじめに

大企業でPower Automateのフロー展開を担当している。現在稼働しているフローは50本以上で、SharePointリスト・Dataverse・Teamsへの通知が主な用途だ。

最近「Apply to eachが遅すぎる」という現場の声があって、並列実行の設定を試した。結果は速くなった。しかし全部のフローに適用したら問題が出た。その試行のまとめだ。

## Apply to each（繰り返し）の並列実行とは

Power Automateの「Apply to each」アクションは、リストや配列の各要素に対して処理を繰り返す。デフォルトは逐次実行（1件ずつ）で、100件あれば100回順番に処理する。

「並列実行を有効にする」オプションをONにすると、各繰り返しが同時に（最大50並列）実行される。100件を最大50並列で処理すると、2〜3ターンで終わる。

設定箇所はApply to eachアクションの右上の「…」メニュー→「設定」→「並列制御」をONにする。「度数（Degree of Parallelism）」で同時実行数を1〜50の間で設定できる。

## 実際に測った：逐次 vs 並列

SharePointリストの100件を読んで、各行に対してTeamsにメッセージを送るフローで測定した。環境：Microsoft 365 E3、SharePointリスト1,000行規模のサイト、Power Automate Premium。

| 設定 | 実行時間 | 備考 |
|---|---|---|
| 逐次実行（デフォルト） | 約4分30秒 | 1件あたり約2.7秒 |
| 並列20 | 約35秒 | 約7.7倍速 |
| 並列50（最大） | 約20秒 | スロットリングエラーが一部出た |

並列20は速く、エラーもなかった。並列50は速いがTeamsへのリクエストが集中してスロットリングが出た。

結論：「とりあえず20」が今の自分たちの設定だが、コネクタや件数によって変わる。実測が必要。

## 設計判断1：順序依存の処理に並列実行は使わない

### 何が起きたか

SharePointリストの行を読んで、連番を採番していくフローがあった。処理のロジックは「現在の最大番号を読む → +1する → その番号で書き込む」という流れだ。

並列実行にしたところ、同じ番号が複数件書き込まれた。

原因は明確だった。並列では「最大番号を読む」が同時に複数の繰り返しで実行される。どの繰り返しも同じ値（例：100）を読む。それぞれが100+1=101で書き込もうとする。結果、番号101が50件できあがった。

これはデータベースの競合状態（Race Condition）と同じ問題だ。Power Automateは「アプリケーションコード」として扱われるため、ストアドプロシージャのようなトランザクション制御がない。

### 設計判断

採番・連番・累積集計（合計を+1ずつ増やすなど）は並列実行にしない。これらは前の処理の結果に次の処理が依存している（順序依存）。

採番を並列処理の外に出す設計にする。例えばDataverseのオートナンバー列、SharePointの専用カウンター列（別のフローで管理）、またはAzure Functionsでのアトミックな採番APIを使う。

並列実行が安全なのは「各繰り返しが互いに独立している」ケースだ。ファイルの読み取り・変換・別々のユーザーへの通知送信などは相性がよい。

## 設計判断2：コネクタのスロットリング上限を把握してから設定する

### 何が起きたか

SharePointの特定のリストに100件同時に書き込もうとしたとき、一部が「429 Too Many Requests」で失敗した。

SharePointにはAPIスロットリング（リクエスト数制限）がある。短時間に大量のリクエストが発生すると、SharePoint側がリクエストを拒否する。Power Automateは内部でリトライを試みるが、すべてのリトライが失敗するとアクションはエラーになる。

スロットリングの上限はコネクタごとに異なる。

| コネクタ | スロットリング参考 |
|---|---|
| SharePoint | テナント全体で1秒あたりのリクエスト数に上限あり |
| Teams（Webhookなど） | チャネルへの1分あたりのメッセージ数に上限 |
| Dataverse | 環境ごとにAPIコール数の上限あり |
| Office 365 Outlook | Exchange管理センターの設定による |

詳細はMicrosoft公式ドキュメントで確認してほしい。上限の具体的な数字はテナントの契約プランやバージョンによって変わる。

### 設計判断

並列実行の「度数」を使用するコネクタのスロットリング上限に合わせて設定する。まず5〜10程度から試し、エラーが出ない数値を実測で探す。

::: note info
Power Automateには「再試行ポリシー（Retry policy）」の設定がある。429エラーが出たとき自動でリトライする設定だ。これを有効にしておくと、スロットリングが一時的な場合に自動回復する。ただし並列実行数を下げる根本的な対策の代わりにはならない。
:::

1コネクタへの同時アクセスが集中する場合は、並列実行数を制限する方が安全だ。逐次で2分かかるのと、並列でスロットリングエラーが出て再実行が必要になるのを比較したとき、前者の方が安定している場合がある。

## 設計判断3：エラーのデバッグが難しくなることを前提に設計する

### 何が起きたか

逐次実行のフローでエラーが出ると、実行履歴で「何件目で止まったか」がすぐ分かる。エラーの直前の処理が何かも分かる。

並列実行にすると、複数の繰り返しが同時に動いているため、実行履歴が入り組んでいて読みにくい。50並列で動いている中から、1件だけ失敗していたケースを見つけるのに時間がかかった。特に「特定の入力データのときだけエラーになる」というケースで、失敗した件のデータを特定するのが難しかった。

実行履歴を展開したときの表示も、逐次実行より情報が多く処理のタイミングが入り混じって表示される。

### 設計判断

並列実行にするフローでは「エラーログ」を設計に含める。具体的にはApply to each内に以下を追加する。

1. `Configure run after` の設定で、このアクションが失敗したときに「エラーログ書き込み」アクションが動くようにする
2. エラーログには「繰り返し番号（index()関数）」「入力データの識別子」「エラーメッセージ（result()関数）」を含める
3. ログの書き込み先はDataverseのテーブルかSharePointリストにしておくと、後からフィルタして確認できる

```
エラーログの例（Dataverseテーブル）
- 実行ID：triggerOutputs()?['headers']?['x-ms-flow-run-id']
- 繰り返し番号：items('Apply_to_each')?['番号']（元データの識別子）
- エラー詳細：result('エラーが出たアクション名')?[0]?['error']?['message']
```

::: note warn
`result()`関数は現在のアクションの結果を参照するため、`Configure run after`の設定が必要になる。設定なしで`result()`を呼ぶと「このアクションが実行されていない」という別のエラーになる場合がある。
:::

## 並列実行が向いているケースと向いていないケース

以下をまとめると判断基準になる。

**向いているケース**
- 各繰り返しが互いに独立している（順序依存なし）
- 外部APIや同一コネクタへのアクセスが分散している
- エラーログが設計されている
- 処理時間の短縮がユーザー体験・業務上の要件として必要

**向いていないケース**
- 採番・累積集計など前の処理の結果に次の処理が依存している
- 同じコネクタに対して短時間に大量のリクエストを送る
- Apply to each内の処理が複雑でデバッグに時間がかかる可能性がある
- フローが業務の中心的な処理で、エラー時の影響が大きい

## この検証の限界

今回の結果は、特定のテナント（大企業・Microsoft 365 E3）での実測だ。テナントごとのスロットリング設定、フローの総数・同時実行数、コネクタの種類によって結果は変わる。

「並列20で問題なかった」という数値は、あくまで当方の環境での話だ。別のテナントでは10で頭打ちになることも、50でも問題ないこともある。実測で確認することをお勧めする。

またPower Automateのバージョンアップで並列実行の制限や動作が変わる可能性がある。本記事の執筆時点（2026年11月）での話で、最新の仕様はMicrosoft公式ドキュメントで確認してほしい。

並列実行のパフォーマンス計測についても、テスト環境と本番環境でリストのサイズや他のフローの同時実行状況が違う場合は数値が変わる。今回の「約8倍」はテスト環境での計測だ。
