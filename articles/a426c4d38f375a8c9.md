夜中に動かした Claude Code のジョブが、翌朝ログを見たら止まっていた。終了コードは 0 のまま、処理は途中で終わっていた。「成功した記録がない = 何かがおかしい」という検知の仕組みを入れていなかったために、24 時間以上気づかれなかった。

`claude -p` を使ったスケジュール実行（夜間バッチ）を数ヶ月動かして、設計で気をつけるべきことが3つ見えてきた。実際に踏んだ問題をもとに整理する。

## 1. ツール権限は「してはいけないこと」から逆算して設計する

Claude Code は実行時に使えるツールを設定ファイルや `--tools` フラグで制御できる。よくある失敗は2パターンある：「全部許可したまま放置」と「絞りすぎて必要な操作ができない」だ。

設計のポイントは「このジョブが触ってよいリソースはどこか」を先に決めること。例えば「記事をファイルに書いて CSV に追記するだけのジョブ」なら：

**許可する：**
- 特定ディレクトリへのファイル読み書き
- `node` スクリプトの実行（対象スクリプトを列挙）

**禁止する：**
- `git push`（意図しないリモートへの影響）
- `rm -rf` などの削除系コマンド
- 環境変数を出力するコマンド（API キーの漏洩リスク）

`.claude/settings.json` の `allow` / `deny` でコマンドパターン単位に制御できる。**最初に禁止リストを書き、残りを許可リストで絞る**設計の方が、「うっかり許可しすぎ」を防ぎやすい。

```json
{
  "permissions": {
    "deny": [
      "Bash(git push*)",
      "Bash(rm -rf*)"
    ]
  }
}
```

権限の設計は「なにができるか」ではなく「なにをしてはいけないか」を先に定義する方が漏れが少ない。

## 2. コストは「最悪値」で見積もる——ターン数 × モデルが支配的

`claude -p` の1回あたりのコストは実行ごとにばらつく。同じプロンプトでもターン数（ツール呼び出しの回数）とモデルによって金額が大きく変わる。

ツール呼び出しのたびに入力トークンが積み上がる構造なので、ターン数が多いほどコストは指数的に増える。実際のデータで言うと：

| ターン数の目安 | コストの目安（参考値）|
|---|---|
| 5〜10 ターン | $0.10〜$0.50 程度 |
| 50 ターン前後 | $1〜$3 程度 |
| 100 ターン超 | $5 以上になる場合もある |

月のコスト管理には「このジョブが毎日最悪値で走ったら」の計算を先に入れておくと、上振れしたときに慌てなくて済む。

ターン数を削る方法としてプロンプトに書いておくと効果があるのは：
- 「同じファイルを二度読まない」
- 「確認だけの追加検索をしない」
- 「複数ファイルへの書き込みは1回の操作にまとめる」

記事の質・処理の精度は落とさず、**事務的な確認作業の回数だけ削る**のが原則だ。

## 3. 障害検知は「Claude の起動前後」の両方をカバーする

`claude -p` が完全に起動できない状態（認証切れ・ネットワーク障害）では、Claude 自身が持つ通知機能（PushNotification ツール）は使えない。「ジョブが起動した後の通知」に頼るだけでは、起動前の障害が見えない。

実際にあった問題：OAuth トークンが期限切れになり、`claude -p` 自体が起動できなくなった。Claude が通知を送れない状態なので、ジョブは無音で失敗し続けた。24 時間以上見逃された。

設計として入れた層：

1. `claude -p` を呼び出すシェルスクリプト（Node.js）が**終了コードと JSON 出力**を受け取る
2. 失敗（終了コード非 0 または JSON 破損）を検知したら、Claude に頼らず**直接 HTTP で通知**を送る
3. 成功した記録も日付つきで残す。翌朝「今日まだ成功していない工程」を自動で再実行できるようにする

```javascript
// シェルスクリプトの概念的な構造
const result = await runClaudeP(prompt);
if (!result.success) {
  // Claude に頼らず直接通知
  await fetch('https://ntfy.sh/your-topic', { method: 'POST', body: 'ジョブ失敗: ' + result.error });
}
// 成功記録を書く
await appendLog({ step: 'daily-run', date: today, success: result.success });
```

「通知が来ない = 成功した」ではなく「**成功の記録が来た = 成功した**」に設計を変えると、無音の失敗を見逃しにくくなる。

## まとめ

- ツール権限は「してはいけないこと」から逆算し、禁止リストを先に書く
- コストは最悪値で見積もる。ターン数 × モデルが支配的変数。プロンプトで事務作業の回数を削る
- 障害検知は Claude 起動前後の両方をカバーする。「成功の記録が来た = 成功」の設計にする
