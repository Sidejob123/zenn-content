Dify 1.18.0が2026年10月23日にリリースされた。Dify Enterpriseを本番で運用している立場からリリースノートを読んで、設計に関わる変更点を整理した。速報よりも「実際に何が変わるか・何を確認しなければならないか」に寄せて書く。

出典：https://github.com/langgenius/dify/releases/tag/1.18.0（2026年10月23日）

## Output Routes——エージェントが自分でワークフローの分岐先を選べるようになった

今回の変更の中でいちばん設計に直結すると感じたのがOutput Routesだ。

これまでDifyのエージェントで条件分岐を実現しようとすると、エージェント自身にプロンプトで「〜なら〜を呼べ」と書く方法が主流だった。エージェントの推論に分岐を委ねる形なので、同じ入力でも違うパスに進むことがあり、テストが難しかった。

Output Routesでは、ノードに複数の出力ルートを設定し、それぞれの選択条件を設定として定義できる。エージェントは「switch output」という読み取り専用の出力でどのルートを選んだかを公開する。条件の設計がワークフロー側に移ったことで、「この入力パターンならこのパスに行く」という期待値のテストが書きやすくなる。

現場での使い道としては、たとえば次のような場面を想定している：

- ユーザーからの問い合わせが「一般情報の照会」か「サポートケースの起票」かでルーティングを分ける
- エージェントの返答が「回答済み」か「エスカレーション必要」かで後続フローを切り替える
- 書類のレビュー結果が「承認」「条件付き承認」「差し戻し」で次のステップを変える

プロンプトに分岐ロジックを書いていた部分を、ワークフローの設定として外に出せるのは保守性の観点でも大きい。ただし条件の設定方法の詳細（条件式の書き方・型の扱い）はGA後のドキュメントを確認する必要がある。

もう一点、「Plain Agent v2ノードがテキストをストリームで出力するようになった（#43986）」という変更も記載されている。構造化結果・ルーティング済み結果・デフォルト値エラーハンドリングを使っているノードはバッファされたままで変わらない。この違いを理解していないと、ストリーム前提のフロントエンドが想定外の挙動をすることがある。

## .ifpkgによるポータブルアプリ——環境間移行が一つのパッケージに

アプリをその依存リソースごと単一の `.ifpkg` パッケージとして移動できる機能が追加された。WorkflowとChatflowのパッケージには、インラインのAgents・Skills・その関連ファイルが含まれ、インポート時に移動先のワークスペースでリソースが再作成され、参照が再マッピングされる。

Dify Enterpriseで複数環境（開発・ステージング・本番）を運用している場合、アプリの昇格手順がこれで変わる可能性がある。これまでDSL（YAML）のエクスポート・インポートを使っていた場合でも、依存するAgentやSkillを別途移行する手間があった。.ifpkgはその一括化を目的としている。

File importとURL importの両方をサポートし、YAMLの明示的なエクスポートは引き続き使える。エクスポート先がYAMLのみの環境では無理に移行する必要はない。

実際に使う前に確認したいのは次の点だ：

- 認証情報（API keyなど）はパッケージに含まれるのか、含まれない場合は移行後の再設定が必要になるか
- 大規模なアプリ（多数のSkillと依存ファイルを持つもの）でのインポート時間と信頼性
- バージョン差異のある環境間でのインポート（開発環境でテストしたパッケージを古いバージョンの本番にインポートするケースなど）

リリースノートには「imports recreate those resources in the destination workspace and remap references」と書かれているが、競合（同名リソースが既に存在するケース）の扱いについては詳細が出ていない。本番環境への適用前に、ステージングで一度試すことを勧める。

## ネストしたワークフローの可視化——デバッグが格段に楽になった

「ネストしたワークフロー実行の中を見られる（Nested Workflow Visibility）」は、地味に見えて実は大きな改善だ。

これまでWorkflow Toolを呼び出すフローをデバッグするとき、子ワークフローの実行履歴は親からは見えず、子ワークフロー側で別途履歴を確認する必要があった。Dify Enterpriseの大企業導入では、複数のWorkflow Toolを組み合わせた多段のエージェントを作ることがある。そういった構成では、どのステップで何が起きたかを追うのが難しかった。

今回、実行履歴からWorkflow Tool呼び出しを開くと、子ワークフローの個別ステップを検査できるようになった。ネストしたToolが子グラフとして実行され、一時停止・再開・停止・ファイル出力が協調して動く。アクセス権限はソースアプリの内容を保護する形で設計されている。

ただし「Nested usage and step totals can still be approximate, particularly after a pause or stop」という注記がある。一時停止・停止後の合計使用量の数字は参考値として扱うべきだということだ。課金管理の観点でこの数字を使っている場合は注意が必要だ。

コンソールでのドリルダウンと外部トレースエクスポートでは対象範囲が異なる点も確認しておきたい。

## Agent Knowledge Base（β）——設計に影響する変更

Agent Knowledge Base機能はベータとして追加されたが、これは「オプトイン」の機能で、エンタープライズ環境での採用を決める前にいくつかの判断が必要だ。

機能としては、エージェント専用のナレッジスペースを作り、ファイルや接続ソースを追加し、ドキュメント処理・メタデータ・検索トレース・品質評価を一か所で管理できる。新しいKnowledge Retrievalノードとエージェント統合はアクセス制御済みのKnowledgeFSスペースを共有する。従来のClassic Knowledgeも引き続き使える。

注意が必要な点が複数ある：

**別サービス・別データベースが必要**：Agent Knowledge Baseは独立したサービスとデータベースが必要で、デフォルトのDocker Compose設定ではオフになっている。有効化するには専用のDB・マイグレーション・KnowledgeFSの設定・モデルプロファイル（埋め込み・推論・再ランク）・ワークスペース移行ゲートの設定が必要だ。IT部門への追加インフラ調達依頼が発生する可能性が高い。

**amd64のみ**：「The published default KnowledgeFS API image is currently amd64 only」とある。ARM環境（Apple Silicon Macを含む開発環境）では動作しない。本番がamd64前提なら問題ないが、開発環境の構成が変わる可能性がある。

Classic Knowledgeが引き続き使えるので、既存のRAG構成をすぐに移行する必要はない。ただし「エージェントに専用のナレッジ空間を持たせたい」という設計をしている場合は、このβをスモールスタートで試す価値がある。

## difyctl——OpenAPIベースのCLI管理

APIとdifyctlを使ってアプリのビルドと管理ができるようになった。CLIはサーバーのオペレーションカタログからコマンドを検索し、ヘルプをサポートする。Workflowとchatflowの作成・DSLインポート・エクスポート・設定・環境変数・公開・バージョン復元に対応している。

使用する前に再サインインが必要な点と、「Draft hashes protect concurrent edits」という仕組みが入っていることに注意。並行編集のロック管理がCLI経由でも効くようになっているということだ。

CI/CDパイプラインにDifyのデプロイを組み込む場合、このdifyctlは選択肢になる。ただしCLIの安定性（コマンドの互換性・バージョン対応）については、β段階のため今後変わる可能性がある。重要な本番デプロイを自動化する前に、コマンドの変更履歴を追える体制が必要だ。

## アップグレードで注意した点

リリースノートのアップグレードガイドは詳細で、読み飛ばすと詰まる項目がいくつかある。Dify Enterprise環境に適用する前に確認した内容をまとめる。

**依存バージョンの変更**：
- Python 3.13が必要（APIとワーカー）
- Node.js 24.22.1以上（24.x系）、pnpm 12.10.1
- 依存関係のロックファイルのリフレッシュが必要

**Agent Backendと関連コンポーネントの同期アップグレードが必須**：
`/runs`エンドポイントがcomposition v2を受け付け、v1リクエストを拒否するようになった。既存のセッションスナップショットは読み取り時にv2に変換されて保存されるが、古いランタイムは新しく保存されたv2スナップショットを読めない。Agent BackendとAgent runtimeを同時にアップグレードしないと、両者が不整合な状態になる。

**AskHumanツールとdeferredレジュームパスの削除**：
古いエージェント専用のAskHumanツールと`deferred resume`パスが削除された。これを使っていたワークフローは修正が必要だ。共有のWorkflow Human Inputノードは引き続きサポートされている。

**Localサンドボックストークンの設定**：
restart前に設定が必要。`--require-auth-token`フラグは1.17.1のAgent Backendランタイムイメージがサポートしていないため、1.18.0のイメージとセットで更新が必要。

**パスワードハッシュ設定の維持**：
`PASSWORD_PEPPER`を設定している環境では、アップグレード後も同じ値を維持しないとパスワード不一致が起きる。「既存インストールでpepperが未設定の場合は`PASSWORD_PEPPER`を空のままにしておく」とある。これを変えてしまうと本番ユーザーのログインが全員できなくなる。

**in-flightのrunが終わるのを待つ**：
「Retire old workflow consumers before admitting new-version traffic. Let in-flight runs finish, then replace legacy workers.」とある。メンテナンスウィンドウを設けてアップグレードすることが推奨されている。

## この検証の限界

今回は公開されているリリースノートの内容を自分の環境の設計に照らして読んだものだ。いくつかの機能（Output Routes・.ifpkg・difyctl）については、実際の本番環境で試した記録ではなく、設計上の読み解きにとどまっている。

実際にOutput Routesを本番ワークフローに組み込んでみたときの挙動や、.ifpkgで複数環境間の移行を試みたときの課題については、別途確認が必要だ。

Agent Knowledge Baseは現時点でβかつamd64専用のため、自分の環境への適用はまだ検討段階だ。導入コスト（別DBの用意）と利益（RAGの集約管理）のバランスは環境次第で変わる。

引き続き実際に動かした結果を記録していく予定だ。変更点・気づきがあれば追記する。
