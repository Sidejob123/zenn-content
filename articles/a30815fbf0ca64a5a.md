## はじめに

大企業でAI・デジタル化推進を担当している。Power Automateの承認フローを構築・展開する案件を18件ほど経験した。毎回同じ場所で詰まる。タイムアウト、代理承認、並列承認のエスカレーション処理だ。

この記事では、繰り返し発生した3か所の問題と、現在使っている対処記録をまとめる。Power Automateのドキュメントに書かれていない運用上のポイントが多いため、設計を始める前に読んでおくと詰まる時間が減るはずだ。

**TL;DR（結論）**：
- 承認タイムアウトは「デフォルト30日でよい」は間違い。業務の締め切りと合わせて設定する
- 代理承認は「承認者が不在の場合」だけでなく「承認者アカウントが無効化されたとき」も考慮する
- 並列承認の「全員の承認が必要」は、一人でも拒否したときの処理を別で設計しないと止まる

## この記事で分かること

- 承認タイムアウトの設定と、タイムアウト後の処理のパターン
- 代理承認（委任）の実装パターンと注意点
- 並列承認での「全員承認必須」設計と、一人拒否時のフロー設計
- 18件の展開で実際に起きた問題と、現在使っている解決策

## 1. 承認タイムアウト——デフォルト30日では業務に合わない

### 問題

Power Automateの「承認の開始と待機」アクションのタイムアウトはデフォルトで30日だ。多くのドキュメントにも「デフォルトのまま使える」と書かれている。しかし実際の業務では、30日待ってから「承認されませんでした」という通知が来ても遅すぎる。

当方で経験した例：
- **見積書の承認フロー**：案件の期限は提出から5営業日。5日以内に承認されなければ案件が消滅するが、タイムアウトが30日に設定されていたため、期限が過ぎた後でも「承認待ち」のフローが走り続けた。期限切れの見積書に対して承認依頼が届き続けた
- **経費申請の承認フロー**：会計処理の締めが月末。月末までに承認されない申請は翌月まわしになるが、30日タイムアウトでは月またぎが発生した

### 対処

**タイムアウト値は「業務の締め切り - 1日」を基準に設定する**。

「承認の開始と待機」アクションのタイムアウト設定は、ISO 8601のDuration形式で入力する：

```
P5D    → 5日間
P3DT4H → 3日と4時間
P1D    → 1日間
```

タイムアウト後の処理は「タイムアウトの実行」ブランチに書く。このブランチを設定しないと、タイムアウト後は何も起きずにフローが終了する。

**タイムアウト後の処理パターン**：

| 業務の要件 | タイムアウト後の処理 |
|---|---|
| 上長にエスカレーション | 承認者リストを変えて再度「承認の開始と待機」を実行 |
| 自動承認（決裁ルールによる） | 申請を承認済みとして次のアクションへ進む |
| 申請を差し戻し・無効化 | 申請者に「期限切れで無効」の通知を送る |
| 管理者に通知して手動対応を依頼 | 管理者にTeams/メールで通知、フローは一時停止 |

「何日でタイムアウトにするか」は業務担当者に確認するしかない。フロー設計者側で勝手に設定すると、業務のルールと合わない値になる。

### この検証の限界

タイムアウトのDuration形式はPower Automateの設計画面で検証した。ただし、タイムアウトの挙動が「フローの実行時間の上限（30日）」と重なる場合は別の挙動になる可能性がある。フロー全体の実行時間が30日を超えるような長期承認は、Power Automateではなく別のツールを検討した方がよい。

## 2. 代理承認——承認者が「いない」ときのパターンは3種類ある

### 問題

承認者が不在（休暇・出張）の場合に代理承認者を設定するのは多くの設計に含まれる。しかし実際の運用では、単純な「不在」以外のケースも起きた。

**ケース1：承認者のアカウントが無効化された**
人事異動で部署を異動したタイミングで、前の承認者のM365アカウントが無効化された。フローに承認者として設定されていたメールアドレスが無効になり、承認依頼が届かなくなった。フローのエラー履歴に「指定されたユーザーが見つかりません」が残った。

**ケース2：承認者の組織が変わった**
組織改編で、承認権限を持つ役職が変わった。フローに「課長」の肩書のメールアドレスを直書きしていたため、次の課長に変わった後も前の課長に承認依頼が届き続けた。

**ケース3：承認者が複数の申請で詰まった**
月末に承認依頼が集中し、承認者の受信トレイが埋まった。優先度の高い承認が低い優先度の申請に埋もれて、期限を過ぎた。

### 対処

**承認者の設定方法を見直す**：承認者のメールアドレスを直書きしない。SharePointリストやDataverseに「承認者マスタ」を持ち、フローはそこから取得する。

```
承認者マスタ（SharePointリスト）
- 申請種別
- 承認者メールアドレス（現在の担当者）
- 代理承認者メールアドレス
- 有効フラグ
- 更新日
```

組織改編や人事異動があったときは、SharePointリストを更新するだけでフローを変更せずに承認者を切り替えられる。

**ユーザーが見つからない場合のエラー処理**：「承認の開始と待機」アクションの設定で「アクションが失敗した場合の実行」を追加する。承認者アカウントが無効化されていた場合はここで管理者に通知する処理を書く。

**承認者への通知の再送**：承認依頼が届いてから一定時間後にリマインダーを送る処理を別で持つと、「通知を見逃した」という問題が減る。「承認の開始と待機」アクション自体にはリマインダー送信の機能がないため、スケジュール実行のフローで未決の承認を検索してリマインダーを送る方式にしている。

### この検証の限界

上記のSharePointリスト方式は実際に使っているが、SharePointリストの更新がフローのトリガーになるまでにタイムラグがある場合（キャッシュ）があった。重要な承認フローで承認者を変えた後は、テスト実行で確認してから運用を始める方が安全だ。

## 3. 並列承認——「全員の承認が必要」設計の落とし穴

### 問題

複数の承認者全員の承認が必要な場合（たとえば「営業部長と財務部長と情報システム部長の3者全員の承認」）、Power Automateの「カスタム応答の要求者」を使って並列で依頼を出せる。

ここで詰まるのが「一人でも拒否した場合の処理」だ。

「全員の承認が揃ったら次のステップに進む」は設計しやすい。しかし「一人でも拒否したら申請を差し戻す」の処理は、並列承認の中で拒否が起きたタイミングで他の承認者への依頼を取り消さないと、拒否済みの申請に対して他の承認者が承認依頼を受け続けることになる。

実際に起きた問題：財務部長が拒否した申請に対して、その後も営業部長と情報システム部長に承認依頼が届き続けた。両者は「これは否決されたはずでは」と混乱した。

### 対処

**「承認の開始と待機」ではなく「カスタム応答の要求者」を使って個別に処理する**。

並列承認を実装する方法は主に2つある：

**方法A：「承認の開始と待機」の「全員が承認する必要がある」オプション**
- 設定が簡単
- 一人拒否した場合の中断処理が難しい
- 拒否したことを他の承認者にリアルタイムで伝えられない

**方法B：Apply to eachで承認者ごとにフローを分岐させる**
- 設計が複雑になる
- 一人の拒否を検知してフローを止める処理を組み込みやすい
- 「誰が承認してどこで止まっているか」の状態管理ができる

当方では承認者が3名以上の場合はB方式を使っている。フロー設計は複雑になるが、拒否時の通知（「◯◯部長が否決したため申請を差し戻します」）と、申請者への再提出依頼を自動で処理できる。

**状態管理のパターン**：

承認の進行状況をSharePointリストで管理する方式：

```
承認状態管理リスト
- 申請ID
- 承認者1：承認/拒否/未回答
- 承認者2：承認/拒否/未回答
- 承認者3：承認/拒否/未回答
- 全体の状態：承認完了/拒否/審査中
- 更新日時
```

各承認者からの応答があるたびにリストを更新し、「いずれかが拒否→全体を拒否に更新してフローを終了」「全員が承認→全体を承認完了に更新して次のステップへ」という処理にする。SharePointリストをダッシュボード化して管理者が状態を確認できるようにすると、「今どこで止まっているか」が可視化できる。

### この検証の限界

上記の方式はSharePointリストへの書き込みタイミングで競合（同時書き込み）が起きる可能性がある。同一申請に対して複数の承認者が同時に応答した場合、SharePointの楽観的ロック（同時更新時の409エラー）が発生した例があった。SharePointリストで並列書き込みが発生する可能性がある場合は、DataverseかAzure Table Storageへの切り替えを検討した方がよい。

## 設計に入る前に確認しておくこと

上の3つの問題はすべて「要件定義の段階で決めていなかった」ことで発生した。設計を始める前に業務担当者に確認するリスト：

| 確認事項 | 確認が必要な理由 |
|---|---|
| 承認の期限（何日以内に承認が必要か） | タイムアウト値の設定に影響 |
| 承認者が不在の場合の代理承認者は誰か | 代理承認のルール設計に影響 |
| 承認者が変わる頻度・タイミング | 承認者マスタの更新頻度に影響 |
| 一人でも拒否したら申請はどうなるか | 並列承認の拒否処理の設計に影響 |
| タイムアウト後の処理（自動承認・差し戻し・エスカレーション） | タイムアウトブランチの設計に影響 |
| 承認の履歴をどこに残すか | ログ設計に影響 |

これを最初に確認しないと、フローを作り直すことになる。フローの作り直しは、既存の接続や式の書き直しを伴うため、最初から決まった状態で作るより数倍時間がかかる。

## まとめ（今後の課題として残っているもの）

18件の展開を通して、上の3点は毎回確認するようにした。ただし、まだ解決できていない問題もある。

**承認の「催促」の自動化**：承認依頼から一定時間後に自動でリマインダーを送る仕組みは動いているが、リマインダーを何回送るか・何回送っても反応がない場合のエスカレーション条件は、案件ごとに業務担当者と都度決めている。標準化できていない。

**承認の監査ログ**：「誰がいつ承認・拒否したか」のログはPower Automateの実行履歴に残るが、Power Automateの実行履歴の保持期間は30日（プランによる）。30日を超えたログを参照する必要がある場合は、SharePointやDataverseへの別途記録が必要だ。

設計の手を入れるたびに少しずつ整理できているが、業務が変わると設計も変わるため、完成形はない。
