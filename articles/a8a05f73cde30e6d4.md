本業で Power Automate を使って社内フローを複数運用していると、「動いているフローを変える」ことへの怖さが積み重なっていく感覚がある。

最初の1本を動かすのは難しくない。問題は、そのフローが「本番で動いているもの」になった瞬間から、改修のたびに影響範囲の見通しが悪くなっていくことだ。

この記事では、複数のフローを運用しながら身につけた「変えやすいフローの作り方」を、設計原則として整理する。

## 1. 承認者・担当者の参照をハードコードしない

最もよく見る設計の問題は、フローの中にメールアドレスや名前が直接書かれていることだ。

```
// こうなっていると
承認者: yamada@company.com
```

異動・退職のたびに「フローを直してください」という依頼が来る。しかも直した後に影響を受けるのは、同じ人物が関係する別のフローすべてだ。

**設計の切り替え：**

SharePoint リストに「承認者マスタ」を作り、フローはそこを参照する設計にする。人事異動があったときに変えるのはリストだけで、フロー自体を触らずに済む。

この発想は、システム設計でいう「設定を外に出す」原則と同じだ。フローの中に「何が起きるか」を書き、「誰が関わるか」は外から注入する。

## 2. エラーハンドリングを後付けしない

フローが「動いた」段階でリリースしてしまうことが多い。そうすると、エラーハンドリングは後から問題が起きた後に追加することになる。

後から追加するのは思ったより難しい。エラーの種類によってアクションを変えたいが、既存フローのアクションの前後にロジックを差し込むのは、フロー全体の依存関係を動かすことになる。

**設計の切り替え：**

最初から「このフローが失敗したとき、誰に何を通知するか」を決めてから作る。Power Automate の `Configure run after` で「失敗したとき」「タイムアウトしたとき」のブランチを最初のアクション定義時に設定しておく。

設計が面倒に見えるが、問題が起きてから追加する手間の方がずっと大きい。

## 3. 「動いている」を確認できる状態を設計に含める

3ヶ月後に「このフロー、最後にいつ動きましたか」と聞かれたとき、答えられる状態になっているか。

Power Automate の実行履歴は30日しか残らない。30日以上止まっていたフローは、履歴から「動いているかどうか」がわからなくなる。

**設計の切り替え：**

定期実行フローには、毎回の実行結果（成功・失敗・スキップ）を SharePoint か Teams に書き込むステップを入れる。内容はシンプルでいい。「実行日時・結果・処理件数」の3点を記録するだけで、「最後にいつ動いたか」はリストを見ればわかる状態になる。

これは「ログを残す」ことではなく、「状態を見える化する」という設計上の意図だ。

## 3つの原則をまとめると

| 原則 | やること | やらないこと |
|---|---|---|
| 参照を外に出す | 承認者等をリスト参照 | メールアドレスをフローに直書き |
| エラー設計を先に作る | 最初にエラーブランチを定義 | 動いたらリリースして後から追加 |
| 動作確認の仕組みを入れる | 実行結果を毎回記録 | 30日の実行履歴だけに依存 |

この3つは「作るときの手間を増やす」提案だ。短期的には面倒に見える。ただ、フローが増えて本番運用が続くほど、この手間を省いたコストが積み重なっていく。

正直、自分もすべてを最初から実践していたわけではない。最初の1本は「とにかく動かす」で作り、2本目、3本目と問題に当たりながら、この原則を後から取り入れていった。どれが効いたかは、改修のたびに実感している。
