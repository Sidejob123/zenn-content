AIエージェントへの関心は高い。POCをやってみた、というチームも増えた。それでも本番稼働まで到達しているのは、大企業の中でもまだごく一部のチームに限られている。

MicrosoftやGartnerが毎年出すレポートには「生成AIの業務利用が拡大している」という文字が並ぶ。一方で「本格的に業務プロセスに組み込んで毎日動かしている」エージェントは、体感として10のうち1つ動けばいい方で、数字として出てくる「5%前後」という本番稼働率は、自分の周りの状況と大きくずれていない。

Copilot Studio・Power Automate・Dify Enterprise・Azure API を使って社内のAI基盤に関わってきた立場から、「なぜ本番に上がれないのか」を整理してみる。


## 承認プロセスが、エージェントの自律性と合っていない

企業の中でシステムを本番稼働させるには、セキュリティ審査・法務確認・情報システム部門への申請が必要になる。これ自体は必要なプロセスだ。

問題は、その審査が「エージェントが自律的に判断してアクションを起こす」というアーキテクチャを前提にしていないことだ。

従来の業務システムは「入力→処理→出力の流れが決まっている」ものが多かった。審査する側も「どういう条件のときに何が起きるか」を確認できれば承認できる。しかしエージェントは「状況を見て自分で次の手を決める」設計なので、「全部のケースで何が起きるか」を事前に書き出せない。

「全パターンを網羅して欲しい」という審査側の要求と、「それを前提にしていないのがエージェントの強み」という設計思想がぶつかる。

**結果として起きること**

- POCで動かしていたものが、本番申請に通らない
- 「承認ルールを先に整備してからでないと使えない」と判断されて止まる
- 「人間の承認を必ず挟む設計」に変えると、自動化のメリットが減る

Copilot Studioで構築したエージェントの本番展開で、「エージェントが送信するメールの件名と本文を事前に全パターン登録してほしい」という要求が来たことがある。エージェントの意味がなくなるので、最終的にルール型のフローに設計を変えた。


## データの分類が先に決まっていないと、エージェントに何も渡せない

「エージェントに社内データを読ませたい」というニーズは多い。議事録・メール・規程類・過去の案件データ。これらをエージェントが参照できるようにすれば、精度が上がる。

ただし「どのデータをどの範囲の人に開示していいか」が整理されていない状態で、エージェントにデータを読み込ませると問題が起きる。エージェントは「読めるデータはすべて参照する」ので、アクセス制御が設計されていないと意図しない情報漏洩につながる。

**実際に詰まったパターン**

| 状況 | 何が起きたか |
|---|---|
| 部門横断のSharePointフォルダをナレッジとして登録 | 別部門の機密資料も参照可能になってしまっていた |
| 人事・経理のデータをエージェントに渡す承認を取ろうとした | 「そのデータを外部サービスに送るのか」という懸念が出て止まった |
| 個人情報を含む顧客データを使ったPOCを本番に上げようとした | 法務確認で「まずデータ分類を整備してから」と差し戻された |

データの分類・アクセス制御・外部サービスへの送信可否。これらを整理するには情報システム部門・法務・事業部門が関わる必要があり、「エージェントを作れる人」だけでは進められない。

Dify Enterpriseではデータソースの権限設定をある程度細かくできるが、「どのデータを誰に見せていいか」のポリシー決定は、ツールの問題ではなく組織の問題だ。


## 既存システムとの接続が、最後まで不確定な問題になる

エージェントが「社内のシステムに書き込む」「外部サービスを呼び出す」という動作をするためには、認証・ネットワーク・APIの連携が必要になる。ここが想定より難しい。

**ネットワークの問題**

大企業では社内から外部へのAPI呼び出しを、プロキシを経由させることが多い。そのプロキシが特定のヘッダーを書き換えたり拒否したりすることで、エージェントのAPI呼び出しが失敗するケースがある（Claude Code v2.1.310 の変更ログにもこの種の問題への対応が含まれていた）。

エンドポイントまで到達できるかどうかが、インフラ担当者と一緒に確認しないと分からない状況で開発を進めることになる。

**認証の問題**

社内システムへのアクセスには、ユーザー単位の認証が必要なことが多い。エージェントが自律的に動く場合、「誰として動いているか」の整理が必要になる。

- サービスアカウント（専用のシステムユーザー）を使う：IT部門への申請が必要
- 担当者のアカウントで動く：担当者が離席・異動したときに止まる
- ユーザーごとに認証する：エージェントの自律性が下がる

Power Automateのフローで「担当者のアカウントが退職したら止まった」という事例は実際に起きやすい。エージェントも同じ問題を抱える。

**APIのバージョン管理**

連携先の社内システムがAPIのバージョンを上げたとき、エージェントが使っているAPIが使えなくなる。このメンテナンス負担が「動かし続けるコスト」として後から顕在化する。


## 本番に到達した案件に共通していたこと

壁を越えて本番稼働に到達したケースを振り返ると、共通する特徴がある。

**1. 「人間が最終判断する」設計を最初から入れた**

エージェントが処理して、結果を人間に見せて、承認を得てから次のステップに進む設計。自律性は下がるが、審査が通りやすくなる。Power Automateの「承認フロー」と組み合わせると、「AIが処理して人間が承認する」という構造を比較的スムーズに作れる。

**2. 使うデータの範囲を最初から絞った**

「社内全データを使いたい」ではなく「この部門のこのフォルダにある資料だけを使う」と明示した上でPOCを始め、そのまま本番の設計にした。範囲を絞ることで、データ分類の承認を取る範囲も小さくなる。

**3. スコープが小さかった**

「メール返信の下書きを作る」「定型レポートの骨格を出す」という、1ステップで完結する処理から始めた案件は本番に到達しやすかった。「複数システムをまたいで自律的に処理する」設計は、ほぼ全部POCで止まっている。


## この分析の限界

- ここに書いているのは、自分が直接関わったプロジェクトと、コンサルとして相談を受けたケースに限られる。業種・企業規模・ITの成熟度によって障壁の種類は変わる
- 「本番稼働率5%」という数字はMicrosoftやGartner等のレポートで繰り返し引用される数字だが、定義（「本番」の基準）がレポートによって異なる。感覚値として参照するのは有効だが、自社の状況と比べるときは注意が必要
- 2026年10月時点の状況。ツール（Copilot Studio・Dify・Azure AI等）のアップデートで、上で書いた技術的な壁の一部は今後変わる可能性がある
- 「本番稼働できている5%」の共通点についても、サンプルが少ないため、これが「本番化のための条件」とは断言できない。現時点での観察として読んでほしい
