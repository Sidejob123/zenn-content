## はじめに

大企業でAI・自動化の推進をやっている。仕事では主にPower AutomateやCopilot Studioを使い、個人では同じような自動化の仕組みをWSL2上のNode.jsで動かしている。

Playwrightを使ってWebページのスクリーンショットを撮ったり、Chromiumでコンテンツを生成したりする処理がいくつかある。ある日、そのスクリーンショットに含まれる日本語テキストが「明らかに日本語フォントではない」形で表示されていることに気づいた。

中国語フォントとしか呼べない見た目だった。内容は読める。でも雰囲気が完全に違う。サービス上に公開するコンテンツに使う画像なので、そのまま放置するわけにはいかなかった。

## TL;DR

- **問題**：WSL2（Ubuntu）上のPlaywright/ChromiumでレンダリングされたHTMLの日本語テキストが、中国語のSimSun・WenQuanYi系のフォントで表示された
- **根本原因**：最小構成のWSL2にはNoto Sans CJK JPなどの日本語フォントが入っておらず、fontconfigがNoto Sans CJK SC（中国語）にフォールバックしていた
- **解決策**：`fonts-noto-cjk`をインストールし、`fc-cache -fv`でキャッシュを更新した
- **副作用なし**：他の処理に影響は出ていない

## 問題の発見

Playwrightでページを開いてスクリーンショットを撮るスクリプトは、ずっと動いていた。ある日、生成した画像をPCのブラウザで開いて「何かおかしい」と気づいた。

日本語のメインテキストが、見慣れない字体になっていた。フォントの種類を変えた覚えはない。HTMLのCSSにも`font-family`は指定していなかった。ブラウザがフォールバックとして何かを選んでいる、ということは分かった。

`fc-list`をWSL2のターミナルで実行してみると、インストールされているフォントの一覧が出た。Notoフォントは入っていたが、「CJK」という単語の後に続く文字を見ると、日本語（JP）よりも中国語（SC）のフォントが先に並んでいた。

## 仮説1：ロケール設定の問題

最初に疑ったのはロケール設定だ。`locale`コマンドを実行した。

```
LANG=ja_JP.UTF-8
LC_ALL=ja_JP.UTF-8
```

問題なさそうに見えた。`ja_JP.UTF-8`は設定されていた。でもこれはあくまでシステムのロケールであって、フォントの選択に直接は影響しない。ロケールが正しくてもフォントがなければ、ロケールに合ったフォントには当たらない。

ロケール設定は原因ではないと判断した。

## 仮説2：PlaywrightのChromiumが独自フォントを使っている

次に、PlaywrightがバンドルするChromiumが独自のフォント設定を持っているのではないかと疑った。

Playwrightを使うとき、`npx playwright install chromium`でChromiumをインストールする。このChromiumは通常のシステムChromiumとは別の実行ファイルで、独自の依存関係を持っている。

Playwrightの公式ドキュメントを確認した。フォントに関しては「システムのフォントを使う」と書かれていた。Playwrightが独自のフォントを持ち込んでいるわけではない。

PlaywrightのChromiumは、最終的にはfontconfigを通じてシステムのフォントを参照している。問題はPlaywrightではなく、fontconfigが何を選ぶかにある。

## 仮説3：HTMLのCSS指定の問題

念のため確認した。HTMLの`<style>`にフォント指定がないことを確認。`body { font-family: sans-serif; }`のようなフォールバックだけで、特定のフォントファミリーを指定していなかった。

`sans-serif`というジェネリックファミリーは、fontconfigが最終的にシステムのデフォルトフォントにマッピングする。そのデフォルトが何かは、fontconfigの設定次第だ。

CSSは問題ではなかった。

## 仮説4：fontconfigの優先順位の問題（正解）

fontconfigがどのフォントを優先しているかを確認することにした。

```bash
fc-match 'sans-serif:lang=ja'
```

このコマンドは、日本語の`sans-serif`として何が選ばれるかを表示する。結果は：

```
NotoSansCJK-Regular.ttc: "Noto Sans CJK SC" "Regular"
```

`SC`は`Simplified Chinese`（簡体中国語）だ。日本語向けに`JP`が選ばれるはずのところに、中国語フォントが来ていた。

理由はシンプルだった。WSL2（Ubuntu 22.04）の最小インストールには、日本語フォントとして`fonts-noto-cjk`パッケージが入っていなかった。入っていたのは別の経路でインストールされたCJKフォントで、そこには`Noto Sans CJK SC`しかなかった。fontconfigはインストールされているCJKフォントの中から「日本語をカバーするもの」を選ぶが、JPがなければSCで代用する。

## 解決策：日本語フォントのインストールとキャッシュ更新

```bash
sudo apt-get install -y fonts-noto-cjk
fc-cache -fv
```

`fonts-noto-cjk`は`Noto Sans CJK JP`（および他のCJK言語向けのフォント）を含むパッケージだ。インストールして`fc-cache`でfontconfigのキャッシュを更新した。

再度確認：

```bash
fc-match 'sans-serif:lang=ja'
```

結果：

```
NotoSansCJK-Regular.ttc: "Noto Sans CJK JP" "Regular"
```

`JP`に変わった。Playwrightで同じスクリプトを実行すると、日本語テキストが正しい字体で表示されるようになった。

## なぜ最初から気づかなかったか

Playwrightスクリプト自体は正常に動作していた。エラーが出ていなかった。スクリーンショットも生成されていた。「日本語を表示したスクリーンショット」を目視で確認するまで、問題に気づかなかった。

自動化環境でよくあるパターンだ。処理が成功したという意味では成功していて、品質が落ちているだけ。品質の確認を目視でやっていなければ気づかない。

## 最小インストール環境でのフォント問題への備え

WSL2の最小インストール（`--install`や`apt-get install --no-install-recommends`で構築した環境）では、日本語フォントが入っていないことがよくある。

PlaywrightやPuppeteerを使ってHTMLから画像・PDFを生成する場合、セットアップ時に日本語フォントのインストールを含めておくとよい。

```bash
sudo apt-get install -y fonts-noto-cjk fonts-noto-cjk-extra
fc-cache -fv
```

`fonts-noto-cjk-extra`は追加のウェイト（太さ）を含む。基本的な表示には`fonts-noto-cjk`だけで十分だ。

DockerやCI環境でも同じ問題が発生しやすい。`ubuntu:22.04`の最小イメージにPlaywrightを入れてHTMLをレンダリングする場合、フォントを明示的にインストールするステップを入れておかないと、日本語が中国語フォントで表示される可能性がある。

`Dockerfile`に入れる場合は：

```dockerfile
RUN apt-get update && apt-get install -y fonts-noto-cjk && fc-cache -fv
```

これだけで済む。

## fontconfigの優先順位を明示的に制御する方法

パッケージのインストールだけでは解決しないケースもある。複数のCJKフォントがインストールされていて、fontconfigが期待通りの優先順位にしてくれない場合は、設定ファイルで優先順位を明示できる。

`/etc/fonts/conf.d/64-language-selector-prefer.conf`（Ubuntu系ではこのパスが使われることが多い）に次の内容を書く：

```xml
<?xml version="1.0"?>
<!DOCTYPE fontconfig SYSTEM "fonts.dtd">
<fontconfig>
  <alias>
    <family>sans-serif</family>
    <prefer>
      <family>Noto Sans CJK JP</family>
      <family>Noto Sans CJK SC</family>
    </prefer>
  </alias>
</fontconfig>
```

JPをSCより前に書くことで、日本語向けフォントが優先される。設定後は`fc-cache -fv`を実行する。

ただし今回の問題はフォントがそもそもインストールされていなかったことが原因だったので、この設定ファイルは使わなかった。インストールだけで解決した。

## この検証の限界

- 検証したのはUbuntu 22.04 on WSL2の1環境だけ。他のLinuxディストリビューションや、WSL2以外の環境では挙動が異なる可能性がある
- Playwright以外のレンダリングエンジン（Puppeteer、wkhtmltopdf、Cairo等）での動作は確認していない。いずれもfontconfigを参照するはずなので同じ修正が効くと思うが、断言できない
- `fonts-noto-cjk`以外の日本語フォント（IPAフォント、源ノ角ゴシックなど）でも同様の問題が解消されるはずだが、試していない
- フォントのバージョンによって字体が若干変わる可能性がある。CI環境とローカルで同じバージョンのフォントを使っていない場合、スクリーンショットの差分が出ることがある

## まとめ代わりに

Playwright自体は何も悪くなかった。エラーログも出なかった。生成されたファイルを目で見るまで気づかなかった。自動化された処理が「品質を落としながら成功する」パターンは、数字を監視するだけでは見えない。

日本語コンテンツを生成する処理があるなら、セットアップ時に`fonts-noto-cjk`を入れておくのが手っ取り早い。2行で済む。
