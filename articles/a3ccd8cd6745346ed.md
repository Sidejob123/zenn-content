> **この記事で分かること：**
> - Claude Code の無人実行で「利用上限」が思っていたより早く来る理由
> - 実際のログから見えた「止まる時刻のパターン」
> - コスト（容量）管理のために変えた4つの設計判断

Claude Code を業務の自動化に組み込んで、夜間に無人で動かすようにした。最初の設計はシンプルだった——「23時に全部まとめて動かす」。

ログを見ると、この方針は最初の1週間で3回止まっていた。止まった原因と、その後に変えた設計判断の話をする。

## なぜ夜間に止まったのか

止まった原因はすべて同じだった——**Claude Pro の利用上限（429/529）**。

実際の実行ログ（`capacity-log.jsonl`）を確認すると、問題が起きていたのは決まって23時台だった。

ログから読み取れたパターン：

| 工程 | 実行時刻 | ターン数 | コスト概算 |
|---|---|---|---|
| 記事執筆（最重量） | 17:00 | 113ターン | $5.27 |
| SNS/ブログ補充（再試行） | 21:13 | 84ターン | $3.63 |
| ヘルスチェック | 23:00 | ─ | 上限超過で失敗 |

17時〜23時の6時間に4工程が集中していた。Claude Pro の利用枠はローリング5時間で管理されているため、17時から始まった重い工程の影響が23時まで残り、ヘルスチェックを押しつぶす形になっていた。

:::note warn
利用上限が来ると、動いていたエージェントは **無言で終了する**。ログには残るが、画面には何も表示されない。最初の1週間は「動いたつもりで実は何もしていない日」が複数あった。
:::

## 変えた設計の4つのポイント

### 1. 重い工程を時間帯に分散させた

全工程を夜間にまとめるのをやめた。実測で最も重かった工程から順に、昼間の利用が少ない時間帯へ逃がした。

```
10:00 → 記事執筆（最重量工程）
12:30 → SNS/ブログ補充（前半・急ぐ作業）
15:30 → コンテンツ担当
17:00 → 成長施策・コメント運用
18:30 → SNS投稿準備（後半）
20:00 → ヘルスチェック
01:30（隔日）→ 戦略会議
```

「夜じゃないと容量が競合する」という思い込みがあったが、実際には昼間の対話セッションとの重複は想定より少なかった。重い工程を昼に逃がすことで、夜間の利用枠に余白が生まれた。

### 2. 重い工程を「急ぐ作業」「急がない作業」に分割した

最初は1工程で「今日やるべき全部」をやらせていた。ログを見ると、ターン数が多い工程は途中で止まったときに最初から全部やり直しになっていた。

実測でターン数が増え続けていた工程は、最終的に106ターンに達して上限超過で途中終了、最初からやり直しで $6.4 相当を消費した日があった。

手順書（プロンプト）を「前半：急ぐ・重い作業」「後半：急がない作業」に分けて、別々のタスクとして登録した。途中で止まっても前半が終わっていれば後半だけやり直せばよい。

```bash
# 前半（急ぐ作業）: 12:30 に実行
run-daily-meeting.sh A

# 後半（急がない作業）: 利用枠に余裕がある日だけ
run-daily-meeting.sh C
```

### 3. 「急がない作業」は利用枠に余裕がある日だけ動かす

既存記事の書き直しや新チャネル調査のような「今日やらなくても来週でいい」作業は、毎日動かすのをやめた。

問題は「無人の Claude Code から利用枠を読む手段がない」こと。Claude Code 自体には「今何%使っているか」を返すコマンドがない（APIの利用率照会エンドポイントは推論専用トークンでは叩けない）。

解決策として、別の対話セッション（デスクトップアプリ）が毎日 03:00 に `get_usage` で利用率を読んで `.usage-gate.json` に書き出し、無人スクリプトはその値が両方 50% 以下のときだけ実行するようにした。

```json
{
  "date": "2026-10-10",
  "fiveHourPercent": 42,
  "weeklyPercent": 38,
  "ok": true
}
```

記録が古い（アプリが閉じていた等）ときは安全側で実行しない。「枠がないのに動く」より「枠があるのに動かない」方がマシという設計。

### 4. 失敗したときの「続きから再開」を作った

途中で止まった後の再実行が「最初からやり直し」になっていた。これが容量の二重消費を起こしていた。

各工程の開始時に「今日どこまでやったか」のスナップショットを保存するようにした。具体的には、各コンテンツプールの行数、キューのアイテム数、ログの見出し数を記録する。

同じ日に再実行されると、「今日すでに済んだ作業はスキップ」という指示をプロンプト末尾に自動で付け加える。

```
【今日すでに完了した作業（スキップしてください）】
- Qiitaプールに q-031 を追加済み
- timely-topics の候補を [x] に更新済み
```

この情報があることで、再実行時に「前にやったことを確認し直す」という無駄なターンが減る。

## 設計変更の結果

変更後のログを見ると、夜間の失敗が起きなくなった。同時に、1工程あたりのターン数も下がっていた（115ターン→平均60ターン前後）。

ターン数が減った原因は、容量制限に引っかからなくなったことより、「分割して再開できる構造」にしたことで「最初から全部確認し直す」という無駄が減ったことの方が大きかったと、ログを見て思っている。

利用枠という制約は「モデルが賢いかどうか」とは別の問題だった。スケジューリングとリトライの設計が正しくなれば、モデルの賢さを活かせる環境が整う。

## まとめ

Claude Code の無人実行で詰まったポイントと、変えた設計の4点：

- **時間帯の分散**：重い工程を昼間に逃がす（夜間に全部集中させない）
- **工程の分割**：「急ぐ」「急がない」を分けて別タスクに、ターン数の上昇を抑える
- **利用枠ゲート**：急がない作業は枠に余裕がある日だけ動かす
- **再開の仕組み**：途中で止まっても最初からやり直さない構造にする

Claude Code を「とりあえず動けばよい」で使い始めると、最初にハマるのは「モデルの賢さ」より「利用枠とスケジューリングの管理」だった。設計として当たり前のことだが、LLM の場合は1回の「止まり方」の影響が大きい分、早めに考えておく価値がある。
