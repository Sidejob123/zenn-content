大企業でMicrosoft Copilotの展開を担当していると、必ず「Copilotが嘘をついた」という声が来る。

「メールを送ったと言ったのに、実際には送っていなかった」「議事録の要約に出席していない人の発言が入っていた」「数字を聞いたら、そのドキュメントに書かれていない数字を答えた」。

最初に聞いたとき、「それは使い方の問題では」と思った。だが同じパターンが繰り返されるうちに、「使い方」だけでは説明できない構造的な問題があることが分かってきた。

この記事では、大企業でCopilotを展開してきた経験をもとに、「Copilotが嘘をつく」問題を種類別に整理し、それぞれへのプロンプト設計のアプローチを書く。定量的な比較実験はできていないが、複数の現場で観察してきた内容だ。

> **この記事で分かること：**
> - Copilotが不正確な回答を返す原因のパターン分類
> - プロンプトで対処できるものとできないもの
> - 企業展開で実際に組み込んだプロンプト設計の考え方

## 「嘘をつく」には種類がある

Copilotが不正確な回答を返すとき、原因は一つではない。実際に遭遇したケースを整理すると、おおよそ3つのパターンに分けられる。

**パターン1：知識の空白を「確からしい何か」で埋める**

LLMの基本的な動作として、答えを求められると何らかの回答を生成しようとする傾向がある。「分からない」と言うよりも、それらしい答えを出す方向に設計されていることが多い。

Microsoft Copilot（M365版）でこのパターンが出やすいのは、「社内のドキュメントにない情報を聞いたとき」だ。Copilotがグラウンディング（情報の根拠をSharePointやTeamsの実際のデータに紐付ける）で動いていても、根拠となるドキュメントに情報がなければ、一般的な知識や推測から回答を補おうとすることがある。

具体例：「A部門の今月の採用目標人数は？」と聞いたとき、社内文書に記載がなければ「確認できていません」と返してほしいのに、過去の類似文書から推測した数字を出してくることがある。

**パターン2：参照元を取り違える**

「Xに関するドキュメントを要約して」と頼んだとき、Copilotが意図していたドキュメントとは別のものを参照して答えを返すケースがある。

社内に似たタイトルのファイルが複数存在するとき（「IT方針_v1.docx」「IT方針_v2_最終.docx」「IT方針_最終_修正.docx」のような状況は大企業に多い）、Copilotがどれを参照したかを明示しない場合、返ってくる答えが「最新版ではない」ことがある。

特に問題になるのは、答えが間違っていても一見して正しそうに見える場合だ。古い版の数字を最新のものとして答えられると、確認しなければ気づけない。

**パターン3：指示の省略・暗黙の前提の解釈ミス**

「今月の売上のレポートをTeamsに送って」という指示が、「今月の売上」を過去12か月の平均と解釈されたり、「Teamsに送る」の対象チャンネルが担当者の意図と異なる場所になったりする。

これは「嘘をついている」というより「不完全な指示に対して最もらしい解釈をした」という話に近い。しかし結果として担当者の意図とは違う動作になるため、現場では「Copilotが間違えた」として報告される。

## プロンプトで対処できるもの

3つのパターンのうち、プロンプト設計で対処できる余地が最も大きいのはパターン3だ。次いでパターン2。パターン1は構造上難しい部分がある（後述）。

### パターン3への対処：指示の明示化

指示に含める要素を増やすことで、解釈のブレを減らせる。

**「境界を決める」**：Copilotが参照してよいデータの範囲と、してはいけない範囲を明示する。Copilot Studioのシステムプロンプトで効果があったのは次のような記述だ。

```
あなたが答えてよいのは、提供されたドキュメントの内容に基づく回答だけです。
ドキュメントに書かれていない内容は「確認できていません」と答えてください。
一般的な知識や推測で補わないでください。
```

**「確認すべき項目を指定する」**：会話の中でCopilotが補足情報の確認をするタイミングを作る。

```
タスクを実行する前に、次の情報を確認してください：
1. 送信先（名前またはメールアドレス）
2. 添付ファイルの指定（ある場合）
3. 送信日時（即時か、後日か）
確認が完了したら「確認が取れました。実行します」と答えてから実行してください。
```

このように「実行前に確認ステップを入れる」設計にすることで、指示の解釈ミスを防げるケースが増えた。

**「実行してはいけない範囲を書く」**：「承認なしに外部へのメール送信をしない」「変更前にファイルの保存先を確認する」のような制約を明示する。

### パターン2への対処：参照元を固定する

「どのドキュメントを見て答えるか」をプロンプトに含める。M365 Copilotでは`@ファイル名`でドキュメントを指定できる。Copilot Studioでナレッジソースを設定する場合も、「このSharePointフォルダのこのファイルだけを参照する」という形で絞る方が、意図しない参照を減らしやすい。

```
以下のドキュメントのみを参照して答えてください：
[ドキュメント名・URLを明示]

それ以外のドキュメントや、Copilotが学習した一般知識は参照しないでください。
```

ただし「参照するな」という指示がどこまで厳密に機能するかは、Copilotの内部実装に依存する。完全な保証はないため、「重要な操作の前にCopilotが参照したドキュメントを明示させる」という出力の確認ステップを組み合わせる方が安全だ。

```
答えを出す前に、参照したドキュメント名と該当箇所を1行で示してください。
```

## M365 CopilotとCopilot Studioでプロンプト設計が変わる点

M365 Copilot（チャットやTeamsのCopilot）とCopilot Studio（カスタムエージェント）では、プロンプト設計のアプローチが変わる。

**M365 Copilot（チャット型）**

ユーザーが自由に会話する形のため、システムプロンプトを直接設定できない。制約はユーザーの「使い方の習慣づけ」か、Copilot StudioでカスタムエージェントをTeamsに組み込む形での追加になる。

一般的に有効なのは「@ファイル名で参照するドキュメントを毎回指定する」「実行系の指示は一度に出さず、段階を踏む」という使い方の指導だ。これは「プロンプト設計」というより「使い方のルール化」に近い。

**Copilot Studio（カスタムエージェント）**

システムプロンプト（Instructions）を自分で書けるため、設計の余地が広い。ナレッジソース（SharePointなど）を絞ることで参照範囲を制限できる。アクションにAdaptive Card（承認カード）を挟むことで「実行前の確認」をUIレベルで強制できる。

Azure AI Foundryの「Groundedness評価」と組み合わせると、エージェントの回答が提供ドキュメントに根拠を持つかどうかをスコア付きで定期評価できる。本番環境での品質担保に使える。

## プロンプトだけでは難しいもの

### パターン1（知識の空白を埋める問題）の根本的な難しさ

「知らないと言ってください」という指示は機能することがあるが、完全ではない。

理由は、LLMが「自分が知っているか知っていないか」を正確に判断できないケースが存在するからだ。「知っている気がする」状態でも答えてしまうことがある——これがCopilotの意図しない「自信のある誤答」につながる。

Copilot Studio（RAG構成）では、検索結果が0件のときに「情報が見つかりませんでした」と返す設計にすることで一定の対策になる。しかし「検索結果が0件でも、一般知識から補う」という挙動を完全にオフにする設定は、現状のCopilot Studioでは提供されていない（2026年10月時点・筆者の確認範囲）。

Azure AI Foundryのグラウンディング評価（Groundedness evaluation）を使うと、回答が提供ドキュメントに基づいているかどうかをスコア付きで評価できる。本番環境でCopilot Studioを使う場合、この評価を定期的に実施することが有効だ。

### 「確認ステップ」がユーザーの負担になる問題

プロンプトで「実行前に確認する」ように設計すると、毎回の会話に確認ステップが入り「使いにくい」という声が出ることがある。

これは設計の判断になる。「間違えたときのダメージが大きいアクション（外部送信・ファイル削除・承認フロー起動）は確認必須、読み取りだけのアクションは確認なし」のように、アクションの種類ごとに確認の要否を分けることで、ユーザー体験と安全性のバランスを取れる。

## 企業展開で実際に組み込んだシステムプロンプトの例

社内問い合わせ対応エージェント（Copilot Studio）に組み込んでいるシステムプロンプトの骨格を書く。

```
あなたは[組織名]の社内問い合わせ対応エージェントです。

【回答のルール】
1. 提供されたナレッジベースの内容のみを根拠に回答すること
2. ナレッジベースに情報がない場合は「確認できていません。担当部門への問い合わせをお勧めします」と答えること
3. 外部の一般的な知識を補って回答しないこと
4. 数字・日付・担当者名を答えるときは、必ず根拠となるドキュメント名を添えること

【実行前の確認が必要なアクション】
次のアクションは必ずユーザーの確認を取ってから実行すること：
- ファイルの作成・更新・削除
- メールの送信
- カレンダーへの書き込み

【回答形式】
根拠となる箇所を「（出典：[ドキュメント名]）」の形で1回含めること
```

この設計を入れてから「根拠のない回答」の報告件数が減った実感はある。ただし「何%減ったか」を対照実験で測定できていないため、効果の定量化はできていない。

Copilot Studioのシステムプロンプトの「Instructions」欄は、現時点では文字数制限がある（公式ドキュメントで確認すること。記述量が多すぎると動作が不安定になることがある）。

## ユーザーへの習慣づけと設計の両方が必要

プロンプト設計だけで「Copilotが嘘をつかなくなる」わけではない。ユーザー側の使い方も同時に整える必要がある。

展開現場で伝えてきたことを3点書く。

**①重要な判断には使わない（または二重確認する）**：「◯◯の締め切りはいつ？」という質問の答えをCopilotだけに依存せず、元のカレンダーや文書で確認する習慣を持つ。

**②「参照したドキュメントはどれですか」と聞く**：疑わしい回答が来たら、根拠を明示させる。根拠を示せない回答は信頼しない。

**③実行系の指示は段階を踏む**：「ドラフトを作って確認させて」「送る前に内容を見せて」のように、一度に完結させるのではなく確認ステップを挟む。

これらはCopilotの「嘘」を完全になくすことはできないが、「間違えたときのダメージ」を減らすための設計として機能する。

## この検証の限界

この記事で書いたことには次の制限がある。

- **対象はMicrosoft Copilot（M365 Copilot・Copilot Studio）のみ**：他のLLMサービスに同じ設計が有効かどうかは確認していない
- **Copilotの内部実装は非公開**：「このプロンプトがなぜ効くか」の根拠は外から観察した結果であり、内部の動作原理ではない
- **効果の定量化が不十分**：「報告件数が減った」という定性的な観察はあるが、対照実験はできていない
- **2026年10月時点の動作に基づく**：Copilotはモデルのアップデートが随時行われており、同じプロンプトが将来も同じように機能する保証はない
- **本番環境での直接のテストログを公開できない**：実際のユーザーの会話ログに個人情報が含まれるため

企業での展開において、この記事に書いたプロンプト設計をそのまま本番に入れることは勧めない。テスト環境で動作を確認してから、段階的に適用することが重要だ。
