有料版Copilotを全社展開した直後、こんな報告が来た。「月500件は使ってくれると思っていたのに、先月全部合わせて43件でした。」

似た話を、複数の企業のAI推進担当者から聞いている。導入コストと展開の手間をかけた割に、使われていない。数字を見るたびに、何かを間違えた気持ちになる。

本業でCopilot展開に関わり、相談も複数受けてきた立場から、繰り返し見えてきたパターンを整理する。原因のほとんどは「Copilotの機能が弱い」ではなく「使い方の設計がない」だった。

## 「いつ使えばいいか」が設計されていないと、誰も使わない

導入担当者が陥りやすいのは、「Copilotが何でもできる」という伝え方だ。会議の要約・メールの下書き・文書の質問応答・コードの補完——と列挙すれば機能の広さは伝わる。ただ、これを聞いた現場の人間が最初に思うのは「じゃあ自分の仕事のどこで使えばいいの？」という疑問だ。

答えを持たずに展開すると、こうなる。最初の数日は少し試す。うまくいかない。使うタイミングが分からない。いつの間にか起動しなくなる。

**有効だったアプローチは「業務の単位で使い方を決める」こと。**

抽象的な機能紹介ではなく、「月曜の朝に来るTeamsの長いスレッドは、コピーしてCopilotに投げると5行で要約できる」「定型の会議報告はこのテンプレートで頼むと3分で下書きが出る」という具体例を先に見せる。最初の1件を成功させることが、継続使用への入口になる。

```
悪い伝え方：「Copilotでメールも会議の要約も文書検索もできます」

良い伝え方：「毎週月曜に来る全社メール（400行）をコピーして
　　　　　　Copilotに貼り付けると、3行の要点になります。
　　　　　　まず一度やってみてください。」
```

業務単位で使い方を決めるには、推進担当者が各部門の「毎週繰り返している面倒な作業」を把握している必要がある。ここをスキップして機能説明だけをしても、現場は動かない。

## 第一印象の失敗から回復できないまま放置される

Copilotを使い始めた人が最初に躓くのは、たいていこのパターンだ。

「Copilotに数字を聞いたら、もっともらしい嘘が返ってきた。以来、信用できなくなった。」

これは「Copilot for Microsoft 365」を使っている場合、実際によく起きる。社内のSharePointやTeamsに保存されていないデータをCopilotに聞いても、Copilotはインターネット検索をするか、あるいは存在しないデータを作り出す（ハルシネーション）。

**「嘘をついた」と感じた人が、そのあとどうしたか**を追ったことがある。8割くらいは「使うのをやめた」で終わっていた。誰かが「それはこういう状況だと起きる、こう聞き方を変えると防げる」と教えてくれる機会がなかった。

Copilotの限界と、限界を回避するプロンプトの書き方は、ユーザー自身では発見しにくい。推進担当者が事前に「こういう使い方では嘘が出やすい、こうすれば防げる」を伝えておくか、失敗した人が相談できる場を作っておかないと、第一印象の失敗で使用が終わる。

**具体的な対処：**

- 展開前に「Copilotが嘘をつきやすい質問」のリストを1枚作り、全ユーザーに配布する
- 「Copilotに数字を聞くときは必ず出典（ファイル名・ページ）も一緒に聞く」をルール化する
- 失敗例と成功例を共有するSlackチャンネルやTeamsチャネルを作り、推進担当者が最初の数件を投稿して場を温める

Copilotの嘘を完全に防ぐことはできない。それより「嘘が出たとき、使うのをやめない人を増やす」方が現実的だ。

## 成功体験が組織の中で広まらない

「Copilotで月次報告の作成が半分の時間になった」という人が出てきても、その話が隣の部署に届くことはほとんどない。

なぜか。成功体験の共有は、意図的に仕組みを作らないと起きないからだ。

大企業では特に顕著だ。部署をまたぐ横断的な情報共有の経路がない。同じ部署の中でも「自分だけ生産性が上がった」を積極的に話す文化がない。推進担当者が気づかないまま、使える人と使えない人の差が広がっていく。

**有効だったのは「定量化してから共有すること」。**

「Copilotで楽になりました」ではなく「週に2時間かかっていた作業が30分になった」という数字で共有すると、他のメンバーの反応が変わった。数字があると「自分の業務にも当てはまるかもしれない」という具体的な想像が働く。

定量化が難しい場合は、「Before / After」の比較で見せる。Copilotを使う前の長いメール文章と、Copilotで整理した後の短い要点の比較を並べるだけで、視覚的に差が分かる。

```
共有フォーマットの例：

📌 業務：週次報告メールの下書き（従来20分）
⏱ 変化：Copilotで下書き → 修正5分（75%削減）
📝 プロンプト：「以下の箇条書きから部長向けの週次報告メールを300字で書いて」
結果：[実際のスクリーンショット]
```

このフォーマットで月に1〜2件、推進担当者から共有するだけでも、部署内の認知度は変わってくる。

## IT推進担当と現場のギャップが縮まらない

IT推進担当者は、Copilotの機能を一番よく知っている。それが問題の一部になっている場合がある。

詳しい人ほど、前提条件を当たり前のものとして話しがちだ。「SharePointのページをCopilotのソースとして設定すれば、社内情報を正確に回答できるようになります」と説明しても、現場の担当者には「SharePointのページを設定する」という操作自体が未知のものかもしれない。

Copilotを「使える人」と「まだ使えていない人」の間にある壁は、Copilot自体の操作よりも「どこに何の情報が保存されているか」「どのデータを参照させれば正確な回答になるか」という知識の差であることが多い。この壁は、IT推進担当者にとって自明すぎて見えなくなっている。

**対処として有効だったのは「5分で動くデモ」を部署ごとに用意すること。**

その部署の業務に近いデータ（実際には仮データでよい）を使って、Copilotが正確に回答できる場面を5分で見せる。「自分たちの業務に近い」という点が重要で、汎用的なデモでは「自分には関係ない」で終わる。

推進担当者が各部署の業務を把握して、部署ごとにデモを用意するのはコストがかかる。ただし、このコストを省いてセルフサービスで展開しようとすると、使われない確率が上がる。

## 導入後の測定をしていないと、何も変えられない

ここまで挙げたパターンは、どれも「導入後に何が起きているかを見ていなければ気づけない」。

Copilotの利用状況は、Microsoft 365管理センターの「Copilot の使用状況レポート」で確認できる。ユーザーごとの利用頻度・機能別の使用回数・利用が増えている機能／減っている機能が分かる。

このレポートを月次で確認して、「利用が少ない部署」「使用が止まっているユーザー」を把握し、個別にフォローするサイクルを作る。展開して終わりではなく、展開後の観察と介入が普及の主役だ。

利用が少ない部署に聞いてみると、だいたい次のどれかが出てくる：

- 「何に使えばいいか分からない」
- 「1回試して嘘が返ってきた」
- 「使い方が合っているのか確認する場所がない」

これらはすべて、展開後に介入すれば改善できる。測定なしに「使われていない」で終わると、変えるべきことが分からないまま時間が過ぎる。

## 対処として有効だったことをまとめると

繰り返し見えてきたパターンと、それぞれに有効だった対処を整理する。

| 原因 | 有効だった対処 |
|---|---|
| 「いつ使えばいいか」が設計されていない | 業務単位の具体的な使い方を1〜2件準備して先に見せる |
| 第一印象の失敗で使用が終わる | 失敗しやすい状況と回避策を展開前に配布する |
| 成功体験が共有されない | 数字付きの共有フォーマットを作り推進担当者が最初に投稿する |
| IT推進担当と現場のギャップ | 部署の業務に近いデータを使った5分デモを用意する |
| 導入後の状態を把握していない | 利用状況レポートを月次で確認し使われていない部署にフォローする |

Copilotの機能を変えることはできない。変えられるのは展開の設計と、導入後の関わり方だ。

## この記事の限界

本記事は、大企業でのCopilot for Microsoft 365の展開経験と、相談対応の中で見えてきたパターンをもとにしている。

次の点は確認できていない。

- 中小企業・スタートアップでの展開では、組織構造や意思決定の速さが異なるため、同じパターンが当てはまらない可能性がある
- Copilot for Microsoft 365とCopilot Studio（カスタムエージェント）は別のプロダクトで、普及の障壁の種類が違う
- 2026年秋時点の情報。Copilotのアップデートは頻繁で、機能の正確さや接続できるデータソースが変わる可能性がある
- 利用状況の改善が「業務成果」につながったかの測定は、組織ごとに設計が必要で、汎用的な答えを持っていない
