## はじめに

大企業でAI・デジタル化推進を担当しながら、個人でもClaude Codeを使った自動化システムを運用している。夜間に複数のタスク（記事執筆・SNS投稿・ブログ補充など）をClaude Codeを使って自動で動かす仕組みを作っていた。

ある日、2日間ほぼ何も処理されていなかったことに気づいた。ログには「正常終了」と書いてあった。原因はClaude Codeの利用上限だった。

この記事では、何が起きたのか・なぜ気づかなかったのか・どう設計し直したかを順に書く。同じような自動化を組んでいる人の参考になればと思う。

## TL;DR

- Claude Codeの利用上限に引っかかると、スクリプトはエラーを受け取って終了する
- エラーの種類を記録していなかったため、2日間「正常終了」に見えていた
- 対策は3点：①エラー種別検知と待機、②途中から再開できる状態保存、③1回の実行を短く分割する
- それでも解消できない問題は残っている。正直に書く

## 何が起きたか

### 状況

毎晩0時過ぎに、タスクスケジューラ経由でNode.jsスクリプトが起動する。このスクリプトがClaude Code（claude CLIを呼ぶ形）を使って各種タスクを実行する。

処理の流れはこうだ：

1. タスクスケジューラがスクリプトを起動
2. スクリプトがタスクリストを読む
3. タスクごとにClaude Code（`claude -p <プロンプト>`形式）を呼んで処理
4. 処理結果をファイルに書き出す
5. ログにサマリーを書いて終了

### 2日間動いていなかった

3日目の朝、在庫ファイルを確認したときに気づいた。補充されているはずのファイルが2日分増えていなかった。

ログを見ると、スクリプトの「開始」と「終了」は記録されていた。しかし実際に処理したタスク数は0だった。0件のまま「終了」と書かれていた。

Claude Code CLIを直接呼んでみると、利用上限に関するメッセージが返ってきた。Pro契約の利用上限に達していたため、新しいリクエストを受け付けない状態になっていた。

### なぜ気づかなかったのか

**理由1：処理件数をログに書いていなかった。**

ログには「スクリプト開始（タイムスタンプ）」「スクリプト終了（タイムスタンプ）」しか書いていなかった。実際に何件処理したかを記録していなかった。0件でも「終了」は書かれる。

**理由2：Claude Codeのエラーをスクリプト側でキャッチしていなかった。**

Claude Code CLIは利用上限のとき、標準エラーに理由を出力して終了コード1で終わる。しかしスクリプト側でこの終了コードをチェックしていなかった。catch節で全エラーを「エラーが発生した」と書いてprocessを0で終了させていた。

**理由3：翌日の実行が「昨日何があったか」を見ていなかった。**

毎晩のスクリプトはステートレスで動いていた。前日分が終わっているかどうかを確認せず、常にその日の分だけを処理しようとしていた。前日分がスキップされていても気づかない。

## 設計し直した3点

### 1. エラー種別を検知して待機する

Claude Code（claude CLI）が返すエラーには複数の種類がある。処理の流れの中で区別する必要があるのは主に以下の3つだ：

| エラーの種類 | 意味 | 対応 |
|---|---|---|
| `overloaded_error` | Anthropicサーバーの一時的な過負荷 | 5〜15分待って再試行 |
| `usage_limit_exceeded` | Pro契約の利用上限に達した | 利用枠リセットまで待機（60〜120分） |
| その他のエラー | スクリプトの論理エラー・ネットワーク問題など | ログに記録して次のタスクへ |

利用上限のエラーは`claude -p`を呼んだときのstderrに「You have reached your usage limit」のような文言が含まれる形で返ってくる（バージョンによって変わる可能性がある）。stderrの内容を読んでエラー種別を判定するようにした。

利用上限の場合は90分待機して1回だけ再試行する。再試行でも上限に当たった場合は、そのタスクをスキップしてログに記録し、翌日分のタスクで処理するルールにした。

リセット時刻は公式には非公開だ。実際に動かした記録から、90分待てば通ることが多いという経験値で設定している。正確には分からない。

### 2. 途中から再開できる状態保存

止まることを前提に、「どこまでやったか」を記録する仕組みを入れた。

#### 完了フラグの設計

処理単位（記事1本、投稿1件など）ごとに、処理が完了したら完了フラグをファイルに書く。ファイル名は処理のIDを含めた一意な名前にする。

```
state/
  completed/
    task-article-q116.done
    task-article-q117.done
    ...
  in-progress/
    task-article-q118.lock
```

再起動すると、`completed/`にある`.done`ファイルを確認して、済んでいる処理をスキップする。`in-progress/`に`.lock`ファイルがあれば前回が途中で止まったと判断して、その処理をやり直す。

#### 原子性の確保

フラグの書き込みが途中でクラッシュすると「書いた/書いていない」が曖昧になる。`fs.writeFileSync`で直接`.done`ファイルを書くと、書き込み途中でプロセスが落ちたときに壊れたファイルができる可能性がある。

`fs.renameSync`（一時ファイルを本番のパスに移動）を使うことで、ファイルの「存在/不存在」だけで状態を判断できる。renameはOS側で原子的な操作として扱われるため、中間状態が生まれない。

```js
// 一時ファイルに書いてから、原子的にリネーム
fs.writeFileSync(tmpPath, '');
fs.renameSync(tmpPath, donePath);
```

#### 完了フラグの掃除

前日分の`.done`ファイルが残っていると、翌日の実行でそれらをスキップしてしまう。日付をファイル名に含めて、当日分以外の`.done`ファイルは実行開始時に削除するようにした。

### 3. 1回の実行を短く分割する

元の設計では、全タスクを1回の実行でまとめて処理していた。2〜3時間かかることもあった。これを30〜60分で終わる単位に分けた。

#### 分割の基準

過去ログから「1タスクあたりのClaude呼び出し回数の実績」を集計した。平均的なタスク1回が何回Claudeを呼ぶかが分かると、N回のタスクで使う推定トークン数が計算できる。

1回の実行でPro契約の推定利用量の70%を超えないように、1実行あたりのタスク数を制限した。正確なトークン数は事前に計算できないため、過去実績のコールド推定だ。

#### 分割後の独立性

分割後は各実行が独立している。前半で利用上限に当たっても、後半のタスク群は独立して次の実行を待てる。影響範囲が1実行分に収まるようになった。

タスクを小さな独立したスクリプトに分けたことで、どのタスクが止まったかがログから分かりやすくなった副次効果もあった。

## 解消できていないこと

### 重いタスクの1日遅れ

週次の重いタスク（記事の大量補充・戦略会議相当の処理）は、分割しても1実行で上限に達することがある。その場合、翌日に持ち越しになる。タイムリーな情報（その日の速報記事など）が1日遅れる問題は残っている。

### 昼間の処理との干渉

夜間実行と、日中に人間が行う対話セッション（Claude Proを使って調査・執筆する）が同じ利用枠を共有している。日中に多く使うと夜間の実行枠が減る。逆に夜間に使いすぎると翌朝の対話が制限される。

現状は「日中は重い作業を避け、夜間実行用の枠を残す」という運用ルールで対処しているが、機械的な制御ではない。

### リセット時刻の不確実性

利用上限のリセット仕様（時間帯・リセット頻度・何がカウントされるか）は公式に詳細が公開されていない。実際に動かした経験則で設計しているため、仕様変更があると動作が変わる。

## 朝の通知で確認する仕組み

止まっていることに気づく仕組みとして、朝の通知スクリプトを入れた。毎朝7時に、前夜のタスクログを読んで「処理件数が0だったタスク」をスマホに通知する。

これで2日間気づかないケースはなくなった。ただし通知を見落とすと同じことが起きる点は変わらない。

## この検証の限界

- Pro契約の利用上限の仕様は非公開部分があり、実際の動作から推測している部分がある
- エラー種別の判定は、claude CLIのstdout/stderrのパターンマッチングで行っており、CLIのバージョンが変わると動作が変わる可能性がある
- 状態保存の設計はシングルプロセスを前提にしている。複数プロセスが同時に動く環境では別の排他制御が必要だ
- テストは実際の夜間実行のみで行っており、ユニットテストは書いていない
