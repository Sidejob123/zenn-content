「AIに書かせたコードが動いているかどうか、本当に確認できていますか？」

Claude Codeを使った自動化基盤を数ヶ月動かしてきて、設計の判断として何度も問い直したのがこの問いだ。本業で大企業のAI導入を担当しながら、個人でも複数チャネルへの自動投稿・自動収集・分析パイプラインを動かしている。その中で見えてきた「長く壊れにくい」設計の勘どころを3つ整理した。

> この記事で分かること：
> - AIを使う部分と使わない部分を明確に分ける設計パターン
> - 認証・セッションの有効期限を外部から監視する仕組み
> - 「成功ログ」を盲信しない独立した確認機構の作り方

技術スタックの話というより、「どこを人間が確認すべきか」「どこをAIに任せてよいか」という設計の判断に焦点を当てている。

## 勘どころ1：AIを使う部分と「使わない部分」を明確に分ける

Claude Codeを使った自動化で最初にはまりやすいのが、「Claude（AI部分）とスクリプト（非AI部分）をどこで分けるか」の判断だ。

### プール方式の考え方

一番シンプルな分離パターンは、AIの仕事を「コンテンツを生成してファイルに書く」だけに限定し、実際の送信・投稿・外部APIへのアクセスは**別のスクリプト（Claude不使用）** が担当する設計だ。

```
[AIパイプライン]              [非AIパイプライン]
Claude Code                   node スクリプト
  ↓ 記事を書く                  ↓ CSVを読む
  ↓ CSVに追記する               ↓ APIで投稿する
  (ここで終わり)                ↓ 結果をCSVに書く
```

この設計のメリットはいくつかある：

**コストの分離**：Claudeを呼ぶのは生成フェーズだけで、投稿・収集・集計はClaude不使用で動く。容量消費がどこで起きているかが把握しやすくなる。

**失敗の分離**：Claude（生成）が失敗しても、すでに生成済みのコンテンツの投稿は続く。投稿スクリプトが失敗しても、Claudeによる生成はすでに完了している。それぞれが独立して動いて、独立して失敗する。

**再実行の安全性**：Claudeによる生成を再実行しても、投稿済みのものには触れない（CSVのstatusで管理）。投稿スクリプトを再実行しても、pending状態のものだけを対象にする。

### 分けてはいけない場所

逆に「AIと非AIを混ぜてしまうと壊れやすい」代表例は、**ブラウザ操作とClaude Code呼び出しを1つのセッションで行うことだ**。Playwrightによるブラウザ操作中に利用上限に達してClaudeが止まると、ブラウザセッションが途中で切れた状態になる。再実行すると別のブラウザウィンドウが開く、という複雑な状態になりやすい。

ブラウザ操作は非AIスクリプトとして分離し、Claudeはその操作に必要なコンテンツ（テキスト、設定値、ファイルパス）を用意するだけにする方が、長期的に安定する。

## 勘どころ2：認証の有効期限を外部から監視する

Claude Codeを使った自動化で、無人実行が突然止まる原因の上位に来るのが**認証切れ**だ。しかもこれは「エラーが出ずに静止する」という形を取ることが多い。

### なぜ気づきにくいか

複数の認証が絡む場合、どの認証が切れているかは、エラーメッセージだけでは判断しにくいことがある。たとえば：

- Claude Code自体のOAuth認証
- 自動投稿先サービスのセッションCookie（ブラウザログイン方式の場合、1〜4ヶ月で失効）
- 外部API（QiitaのPersonal Access Token、GitHubのFine-grained Token、Threadsの長期アクセストークン等）

これらが混在している場合、どれが先に切れるかは管理しないと把握できない。そして切れた後に気づくまでの時間が長いほど、その間に積み上がるはずだったコンテンツの損失が大きくなる。

### 「有効期限が近い順に並べる」だけで変わる

シンプルな対策は、**認証ごとの失効予定日を1箇所に書いておく**ことだ。「〇〇のセッションは△月△日ごろに失効予定」という情報を集約しておくだけで、定期チェックのサイクルで「近い順に再認証する」という行動が取れる。

自動化できる場合は：
- 失効予定日まで30日を切ったら通知を出す
- トークンのリフレッシュを自動で行う（Threads長期アクセストークン等はリフレッシュAPIが存在する）

自動化できない場合（ブラウザのCookieが必要なもの等）は：
- 次の失効予定をタスクリストに書いておく
- 失効した場合の再認証手順をドキュメントに残しておく（誰がやってもできる形に）

### 「今、認証は生きているか」の確認頻度

無人実行のサイクルが毎日動いている場合、認証が切れてから最初の失敗に気づくまでは「次の実行時」だ。実行ログにエラーが出ていれば分かるが、「エラーなし・処理なし」という形になる場合は気づくまでにさらに時間がかかる。

Claude Codeを毎日呼ぶサイクルに「各認証の健全性確認」を組み込むと、失敗してから気づくではなく、失効前に気づく構造になる。これは工数がかかるように見えるが、一度組んでしまえば日々のサイクルで自動実行されるため、メンテナンスコストは低い。

## 勘どころ3：「成功ログ」を盲信しない独立した確認機構を持つ

自動化でも手動でも、「処理が成功した」という確認は難しい。「エラーが出なかった」と「期待する変化が起きた」は別の話だ。

### 失敗が無音で起きる3つのパターン

実際に遭遇した「エラーなしに処理が起きていなかった」パターンを3つ挙げる。

**パターン1：投稿スクリプトが「成功」を返すが実際には投稿されていない**

Playwrightでブラウザ操作する投稿スクリプトで、ボタンのクリックが「クリックした」という記録を返しても、実際には非表示の要素にクリックが当たっていて何も起きていないケースがある。DOMに同名の要素が複数ある場合に起きやすい。

**パターン2：ワークフローエージェントがステップをスキップしながら成功と報告する**

Claude Codeのv2.1.301リリースノート（2026-10-15）に修正として記載されていたバグだ。ワークフローの実行結果が「成功」と報告されていても、実際にはステップが実行されていないケースがあった。

**パターン3：Grep/Globが内部エラーで「0件」を返す**

同じくv2.1.301で修正されたバグで、検索プログラムが予期せず失敗した場合に「0件（見つからなかった）」を返していた。「存在しない」と「探すのに失敗した」が区別できない状態だった。

### 独立した確認機構の設計

「成功ログ」への依存を減らすには、**処理の結果を「別の経路で」確認する機構**を持つことが有効だ。いくつかのパターン：

**結果ファイルの増加を確認する**：投稿が成功したかどうかを「投稿ログファイルの件数が増えたか」で確認する。スクリプトが「成功」を返したかどうかではなく、副作用（ファイルの変化）を確認する。

**外部APIで現状を取得する**：投稿後に対象サービスのAPIで「実際に投稿されているか」を取得する。スクリプト自身の報告ではなく、サービス側の現状から確認する。

**定期的な「実績の棚卸し」**：週次・月次で「実績の累計がどう変化したか」を集計し、異常な停滞（数日間変化がない等）をフラグにする。個々の処理の成否よりも、「全体として動いているか」を確認する。

どのパターンも「スクリプト自身の報告を信じない」という姿勢が共通している。これは性悪説ではなく、「AIも非AIもそれぞれ失敗する。どちらが失敗しても気づける経路を持つ」という現実的な設計判断だ。

## 設計の判断を積み重ねるために

3つの勘どころを整理したが、いずれも「最初から完璧な設計を目指す」という話ではない。

- プール方式を導入したのは、最初に「投稿スクリプトが失敗してもClaude分の容量は消えていた」という経験をしてから
- 認証の監視を組み込んだのは、無人サイクルが24時間以上停止してから気づくという失敗を経てから
- 独立した確認機構を考え始めたのは、「成功ログが残っているのに何も変わっていなかった」という場面に何度か遭遇してから

設計の判断は、失敗から逆算して積み上がっていく。今の段階で完璧にする必要はないが、「壊れたときに何が問題だったかを記録する」という習慣が、次の設計判断の精度を上げる。
