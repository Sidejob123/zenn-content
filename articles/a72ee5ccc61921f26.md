大企業の業務システムに生成AI機能を組み込む際、Azure OpenAI Serviceを選ぶケースが増えている。既存のAzure環境との親和性、企業向けのセキュリティ・コンプライアンス対応が理由として挙がることが多い。

ただし、デモや検証環境では動いていたものが、本番システムに組み込んだ途端にレイテンシやコストの問題で運用に耐えなくなる——という話を見聞きする。設計段階で意識しておくべき判断ポイントを整理する。

## 1. モデル選定：「すべてに高性能モデル」は避ける

Azure OpenAI Service のモデルは、高性能なほどコストが高い。簡単な分類・定型要約から複雑な文書生成まで、一律で最上位モデルを使うとコストが積み上がりやすい。

実務的な使い分けの判断軸はこの2つ：

| 軸 | 軽量モデルでよい | 高性能モデルが必要 |
|---|---|---|
| 出力誤りの業務影響 | 小さい（人の確認が入る） | 大きい（出力がそのまま使われる） |
| 処理の性質 | 定型的な分類・要約 | 複雑な判断・高品質な生成 |

段階的なアプローチとして、まず軽量モデルから試し、精度不足が見えた時点で上位モデルに切り替える設計の方が、最初から固定するより結果的にコストと精度のバランスが取りやすい。

## 2. リージョン選定：後から変えるのは痛い

Azure OpenAI Service のデプロイ先リージョンは、情報セキュリティ部門と設計の初期段階ですり合わせる必要がある。企業によっては「データを国内リージョンに限定する」要件がある。

後からリージョンを変更すると、既存のデータ連携やエンドポイント設定を大きく作り直すことになる。加えて、**リージョンによって利用できるモデルの種類やバージョンに差がある**ため、「使いたいモデルが要件を満たすリージョンで提供されているか」を最初に確認しておかないと、要件定義が固まった後で手戻りが発生する。

確認事項のチェックリスト：
- [ ] データ所在地の要件（国内限定 or 特定リージョン限定）はあるか
- [ ] 対象リージョンで希望するモデルが GA（一般提供）されているか
- [ ] プロビジョニングスループット（PTU）の割り当てが必要か

## 3. 同期・非同期の設計判断

業務の性質によって、同期か非同期かが変わる。

**同期呼び出しが向く用途**：ユーザーがチャット画面で応答を即座に待つ場合。ユーザー体験上、レスポンスは速い方がいい。

**非同期処理が向く用途**：大量ドキュメントの一括要約・バッチ処理。API のレート制限（RPM/TPM）に引っかかりやすいため、キューイングを挟んだ非同期設計にする方が安定する。

よくある設計ミスは、PoC段階の同期処理のままバッチ用途に持ち込んでしまうことだ。数十件で動いていたものが、数千件になった瞬間にレート制限エラーで詰まる。業務システムの既存アーキテクチャがどちらの流儀に寄っているかを踏まえ、間にキューやワーカーを挟む設計を検討する。

## 4. PoC → 本番移行の落とし穴

PoC（概念実証）の設定をほぼそのまま本番に持ち込むのは危険だ。PoC は限られたテストデータ・限られた利用者数を前提に組まれていることが多く、本番の利用規模やデータの多様性を想定していない。

本番移行前に見直すべき点：

- **プロンプト設計**：PoCで使ったサンプルデータは、現実のデータの多様性を代表していないことが多い。本番データのばらつきに対してプロンプトが壊れないかを確認する
- **同時アクセス数**：PoC は数人が試す前提で作られている。本番の最大同時アクセス数をシミュレーションする
- **エラーハンドリング**：PoC ではエラーが出てもすぐ人が気づいて対処できる。本番では自動リトライ・フォールバック・通知の設計が必要になる

## まとめ：設計段階で決めておくべきこと

Azure OpenAI API を業務システムに組み込む際に、後から変えると痛い決断を先に整理しておく：

1. **モデル選定**：業務ごとに軽量と高性能を使い分ける設計にする
2. **リージョン**：セキュリティ要件とモデル提供状況を最初に確認する
3. **同期/非同期**：バッチ処理はキューを挟んだ非同期設計を最初から考える
4. **PoC → 本番**：プロンプト・負荷・エラーハンドリングを本番想定で見直す工程を必ず挟む

どれも「分かっていれば後で困らなかった」話だ。デモが動くことと、業務システムとして長期運用できることの間には、見えにくい設計の差がある。
