## TL;DR

Windowsマシン上でWSL2（Ubuntu）を使い、Node.jsのAI自動化スクリプトをタスクスケジューラから動かしている。選んだ理由はPlaywrightのヘッドレス実行と、Windowsとのファイル共有が両立できるからだ。実際に動かすと、パスの扱い・ヘッドレスブラウザの設定・タスクスケジューラとの連携の3箇所で詰まった。この記事はその記録だ。

## はじめに

本業では大企業でAI・デジタル化推進を担当している。個人でもClaude Codeを使ったブログ投稿・SNS自動化の仕組みを動かしている。動いている内容は、毎晩2〜3時に記事を生成してプールに溜め、朝の別スクリプトがブラウザ自動操作（Playwright）で下書き保存するというパイプラインだ。

これをWSL2（Windows Subsystem for Linux 2）上のLinux環境で動かしている。なぜWindowsのNode.jsを直接使わなかったか、どこで詰まったかを書く。コードよりも設計と経験の話が中心になる。

## WSL2を選んだ3つの理由

最初からWSL2を選んだわけではなかった。最初はWindowsのNode.jsで動かそうとして、いくつかの問題に直面してWSL2に切り替えた。

**理由①：Playwrightのヘッドレスモードが安定している**

Playwrightは、Linuxのヘッドレス環境での動作が安定している。WindowsのNode.jsでPlaywrightを動かすことも可能だが、フォントレンダリングやブラウザの起動に関して、Linux環境の方が動作がシンプルだった。今回動かしているのはブラウザ自動操作（認証済みセッションでのブログ下書き保存）で、スクリーンショットが不要なケースが多い。ヘッドレスモードがきちんと動く環境を選んだ結果、WSL2のLinuxになった。

**理由②：Windowsのファイルに `/mnt/c/` でアクセスできる**

Windowsのデスクトップに置いたファイルに、WSL2からは `/mnt/c/Users/user/Desktop/` でアクセスできる。この相互アクセスが、ファイルの受け渡しを簡単にしている。Windowsで生成したJSONファイルを、WSL2のスクリプトが読み取って処理する、という流れが自然に作れた。WSL2を使わずにLinux専用の環境を用意すると、このファイル共有が面倒になる。

**理由③：Windowsタスクスケジューラから `wsl` コマンドで起動できる**

Windowsタスクスケジューラから `wsl -e bash /home/watanabe/scripts/run.sh` のように実行すると、WSL2内のスクリプトを定時実行できる。GUI不要のサーバー的な動作環境がWindowsマシン上に作れる。Linux専用のサーバーを用意するコストなしに、自宅のWindowsマシンを夜間バッチサーバーとして使える。

## 実際の構成（概要）

動いているのは大きく分けて2つのフローだ。

**夜間フロー（23:00〜3:10）**：Claude Code（`claude -p`）を呼び出して記事を生成し、各プラットフォームのプール（CSVやJSON）に溜める。ブログ記事・Qiita/Zenn記事・Threads投稿のテキストをこのタイミングで用意する。Claude APIキーは使わず、Claude Pro（ブラウザ認証）で動いている。

**朝フロー（7:00〜10:00）**：Playwrightを使って、プールにある記事を各プラットフォームに実際に投稿・下書き保存する。Qiita・ZennはAPIで、ブログはPlaywrightのブラウザ自動操作で行っている。

どちらもWindowsタスクスケジューラが起動し、`wsl -e bash` でWSL2内のシェルスクリプトを実行する構成だ。

## 詰まりどころ①：WindowsとLinuxのパスの扱い

WSL2を使うとWindowsとLinuxの両方のパスが混在する。これが最も頻繁に引っかかった箇所だ。

**問題の形**：WSL2のNode.jsスクリプトからWindowsのファイルを読むときは `/mnt/c/...` で問題なく動く。しかしWindowsタスクスケジューラが引数でパスを渡してくる場合や、Windows側のツールが生成したファイルパスをWSL2側で使う場合、`C:\Users\...` の形式のパスが混ざってくる。

**対処**：`wslpath` コマンドを使うと、WindowsパスをLinuxパスに変換できる。シェルスクリプト内で `LINUX_PATH=$(wslpath -u 'C:\Users\user\Desktop\file.json')` のように変換してから使う。逆方向（LinuxパスをWindowsパスに変換）は `-w` オプションを使う。スクリプトの冒頭でこの変換を行い、以降はLinuxパスで統一するようにしてから、パス関連のエラーがほぼ出なくなった。

**もう一つの注意点**：タスクスケジューラの「作業ディレクトリ」の設定が、WSL2内のカレントディレクトリに影響しない。タスクスケジューラで作業ディレクトリを設定しても、`wsl -e bash script.sh` を実行した時点のカレントディレクトリはWSL2のデフォルト（ホームディレクトリ）になる。スクリプトの冒頭で `cd /home/watanabe/projects/tsuglab-automation` を書くようにしてから、この問題が解消した。

## 詰まりどころ②：ヘッドレスブラウザの起動とライブラリの不足

PlaywrightをWSL2上で動かすとき、Linuxの共有ライブラリが不足してブラウザが起動しないケースがあった。

**問題の形**：`npx playwright install` でブラウザをインストールしたにもかかわらず、実行時に「共有ライブラリが見つからない」というエラーが出た。具体的には `libgbm.so.1` や `libxshmfence.so.1` などのグラフィック関連のライブラリだった。

**対処**：`npx playwright install-deps` を実行すると、Playwrightが必要なシステムライブラリを自動でインストールしてくれる。これで大半の問題は解消した。もし動かない場合は `sudo apt-get install libnss3 libnspr4 libatk1.0-0` のように個別にインストールする方法もある。

`xvfb-run` については、今回のユースケースではヘッドレスモード（`--headless`）を明示的に渡しているため不要だった。ただし画面キャプチャが必要なスクリプトでは必要になるかもしれない。

**ブラウザの認証セッションについて**：Playwrightを使ってログインし、認証済みセッションをJSONファイルに保存しておく方式を使っている。ただし一部のサービスは自動化ツールのブラウザを検知してセッションを無効化する。その場合はブラウザの検知をすり抜けるような細工はしない方針にしている。

## 詰まりどころ③：タスクスケジューラとWSL2の組み合わせ

WindowsタスクスケジューラからWSL2を起動する部分に、いくつか独特のハマりどころがあった。

**`~/.bashrc` が読み込まれない**：タスクスケジューラから `wsl -e bash script.sh` で実行すると、インタラクティブシェルではないため `~/.bashrc` が読み込まれない。`nvm` などの環境変数が設定されていない状態になるため、Node.jsが見つからないエラーが出ることがある。解決策は、スクリプトの先頭でパスを明示的に設定するか、シェバン（shebang）を `#!/bin/bash -l` にしてログインシェルとして実行することだ。

**ログの確認方法**：タスクスケジューラから実行したスクリプトのログは、デフォルトでは見えにくい。`>> /home/watanabe/logs/batch.log 2>&1` のようにリダイレクトして、WSL2内のファイルにログを書き出すようにした。深夜のバッチが止まっていたときも、このログを見て何が起きたか分かるようになった。それ以前は「動いているはず」と思い込んでいたが、実際には止まっていたことがあった。

**スリープと実行タイミングの問題**：Windowsホストがスリープ中にタスクスケジューラの実行時刻が来た場合、タスクは「実行された」としてスキップされることがある（スケジューラの設定による）。「コンピュータがアイドル状態のときだけ実行する」「スリープ解除後に実行する」などの設定を確認しておく必要がある。Claude Code v2.1.307では、スリープ後のMCPサーバータイムアウト問題が修正されたが、スケジューラ側の設定も合わせて見直すと安定する。

## 実際に動いているもの

現時点で動いている自動化の概要を書く。数字は実際のプール・ログから取っている。

- Qiita：1日1〜2本、pendingに5〜6件程度を常時維持。毎朝8:45と19:30に自動投稿
- Zenn：1日0〜1本、pendingに2〜3件を維持。朝に自動投稿
- ブログ（FC2・楽天）：週1〜2本、下書きをPlaywrightで保存。公開は人間が行う
- Threads：1日3回（12:10・17:40・21:30）、キューから1本ずつ自動投稿
- 毎朝7時：前日の活動サマリーをスマホ（ntfy）に通知

全部で1日あたり数十回のツール呼び出しが走っている。コストはClaude Pro（サブスクリプション、月定額）の利用枠で賄っている。利用上限に引っかかって深夜に止まることがある。

## この構成の限界

正直に書く。

**スリープ問題は完全には解決していない**：v2.1.307でMCPのスリープ時タイムアウトは修正されたが、そもそもタスクスケジューラがスリープ中にスキップする問題は別物だ。PCの電源設定を「スリープしない」にすれば確実だが、消費電力が増える。現在は深夜だけスリープを無効にする設定を検討中だが、まだ実装していない。

**環境の再現性が低い**：WSL2の設定・nvm・Playwrightのインストール手順が、セットアップメモとして残っていない部分がある。PCを変えたり、WSL2を再インストールする際に同じ環境を再現するのに時間がかかる。Dockerを使えば再現性が上がるが、Playwrightとの相性確認が別途必要になる。

**Windowsのアップデートで動作が変わる可能性がある**：WindowsのメジャーアップデートでWSL2の動作が変わることがある。実際に、あるアップデート後にPlaywrightのブラウザが起動しなくなり、`playwright install-deps` を再実行して解決したことがある。自動更新を無効にしているが、セキュリティパッチとのバランスが難しい。

**検知が遅い**：バッチが止まっていることに気づくのが遅れることがある。朝の通知スクリプトが「昨夜の実行結果」を要約してくれるようになってから改善したが、完全ではない。

## 今回分かったこと

- WSL2でのAI自動化は、パス・ヘッドレスブラウザ・タスクスケジューラ連携の3箇所でほぼ確実に詰まる。事前に知っていればスムーズに通過できる
- `wslpath` でパスを変換し、スクリプト内でカレントディレクトリを明示するだけで、パス関連のエラーの大半は消える
- `npx playwright install-deps` はLinux環境で一度は実行しておく。ライブラリ不足を先回りして解消できる
- タスクスケジューラからのWSL2実行では `~/.bashrc` が読み込まれない。スクリプト側でパスを設定する必要がある
- ログを必ずファイルに書き出す。深夜のバッチが止まっていても気づけるかどうかは、ログがあるかどうかにかかっている
