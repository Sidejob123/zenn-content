## この記事について

大企業でCopilotとPower Automateの社内展開を担当して、200人以上に使ってもらう環境を整えてきた。その過程で「どちらを使えばよいか」という相談を何度も受けてきた。

導入してから「思っていたのと違う」と言われるケースのほとんどは、**ツールを選ぶ前に整理できていなかった問い**がある。3つの問いに答えるだけで、道具選びで詰まる確率がかなり下がると経験から感じている。

なお、この記事は「どちらのツールが優れているか」を比べるものではない。「自分たちの状況でどちらが合っているか」を判断するための整理の枠組みを提供するものだ。

## 問い1：「誰が使うか」でツールが変わる

最初に整理するのは、**ツールを実際に操作する人がどのくらいシステムに慣れているか**だ。

### Power Automateを使う人が必要なスキル

Power Automateは「プログラミング不要」と言われるが、実際には「フローを設計・維持できる人」が必要だ。

具体的には以下のような素養が必要になる：

- トリガーとアクションの関係を理解できる（「何かが起きたら、何をする」という論理）
- 変数と式（ExpressionやDynamic content）を扱える
- エラーが起きたときに原因を調べられる
- 接続（コネクション）とサービスアカウントの管理ができる

プログラミング経験がある人や、Excelのマクロを自分で作ってきた人はスムーズに入れることが多い。一方、PC操作はできるが「仕組みを作る」経験がない業務担当者が一人で始めると、設計・エラー対応で詰まることが多い。

### Copilotを使う人が必要なスキル

Copilot（特に会話型のMicrosoft 365 Copilot）は、自然言語でやりとりするため操作のハードルは低い。

操作コストは低いが、以下の点で別の問題が出やすい：

- 何を聞けば有用な答えが返ってくるか（プロンプトの書き方）が分からない
- 返ってきた内容が正確かどうかの確認ができない
- 業務上のルール（機密・個人情報）をどこまで入力してよいか分からない

「誰でも使える」と言って展開したが、「何に使えばいいか分からない」「答えが合っているか信用できない」という声が出てくるのはこのパターンだ。

### 判断の基準

操作する人が自分でエラーを調べて直せるか、あるいは社内にサポートできる人がいるか → **Power Automateが向く**

業務担当者が自分の言葉でやりとりして使いたい、設計不要で始めたい → **Copilotが向く**

両方の要素がある場合は両方使うことになるが、最初に「誰がメインの利用者か」を決めると計画が立てやすくなる。

## 問い2：「何を自動化するか」で適した道具が違う

次に整理するのは、**自動化したい作業の性質**だ。

### 判断がいらないルーティンの自動化

たとえば「毎朝8時にレポートを取得してメールで送る」「フォームに回答が来たら担当者に通知する」「Excelのデータを別のシステムに転記する」といった作業は、**毎回ほぼ同じ手順で、人間の判断が入る余地がない**。

こういった作業は **Power Automateが向く**。トリガーとアクションを組み合わせると、決まった手順を繰り返し実行できる。処理の途中に「これはどちらにするか」という分岐が入ってくると複雑になるが、条件分岐も設定できる。

### 判断や文章生成が必要な作業

「このメールの内容を要約して返信案を作る」「このデータから報告書の骨子を書く」「会議の議事録を整理して次のアクションをリストにする」といった作業は、**毎回内容が変わり、人間の判断や文章の生成を伴う**。

こういった作業は **Copilotが向く**。毎回同じ手順では処理できない、文脈を読んで答える必要があるものに適している。

### Power Automateの中にCopilotを組み込むパターン

Power Automate + Copilot Studio（またはAI Builder）を組み合わせて「ルーティンの中に判断を入れる」という設計もある。たとえば「フォームに届いた問い合わせをCopilotが分類して、適切な担当者に自動で振り分ける」という構成だ。

ただしこのパターンは設計・検証のコストが高い。最初からこの構成を目指すより、まず「ルーティンの自動化」と「Copilotによる個別アシスト」をそれぞれ単純な形で始めて、慣れてきてから組み合わせる方が現実的だった。

### 判断の基準

毎回同じ手順で処理できる、ルーティンで繰り返しが多い → **Power Automate**

毎回内容が変わる、文章を読んで理解する・文章を書く、判断が必要 → **Copilot**

両方の要素がある → 段階的に始める（最初は単純な方から）

## 問い3：「どこにつながるか」が実装の複雑さを決める

3つ目は**つなぐシステムの種類**だ。ここが一番見落とされやすい点でもある。

### Microsoft 365内で完結するなら比較的シンプル

Outlook、SharePoint、Teams、OneDrive、Excelなど、Microsoft 365のサービス内でやりとりするフローは、Power Automateのコネクタが充実しているため設定しやすい。

Copilotも同様で、SharePointに置かれたドキュメントを読み込ませて回答するといった使い方はMicrosoft 365内で完結する。管理の手間も比較的少ない。

### 外部システムにつなぐと複雑になる

基幹システム（ERPなど）やCRMに接続したい、独自開発のAPIと連携したいという場合は難易度が上がる。

Power Automateには多くのコネクタが用意されているが、自社の基幹システムにコネクタが無い場合は「カスタムコネクタ」を作る必要がある。これにはAPIの知識と、IT部門との連携が必要だ。

Copilotを外部データと連携させるには、Copilot StudioとAPIを組み合わせる設計が必要で、設定・テスト・ガバナンスのコストがかかる。

### セキュリティとガバナンスの確認

外部システムに接続する場合、**どのアカウントの権限でアクセスするか**の設計が重要になる。個人のアカウントで接続を作ると、その人が退職・異動したときにフローが止まる。サービスアカウントを使う運用を最初から決めておく方が安全だ。

Copilotに社外のデータや機密データを読ませる場合は、Microsoft Purview等での情報保護設定との整合性も確認が必要だ。ここが曖昧なまま展開すると、後から「どのデータをCopilotに見せてよいか」の判断を一から作ることになる。

### 判断の基準

Microsoft 365内で完結する → 比較的シンプルに始められる

外部システムと接続したい → IT部門・API担当者との設計が必要。範囲を絞って始める方が現実的

## CopilotとPower Automateの棲み分け（まとめ）

| 観点 | Power Automate | Microsoft 365 Copilot |
|---|---|---|
| 操作者 | フロー設計ができる人（IT系の素養が要る） | 一般業務担当者（自然言語でやりとり） |
| 向く作業 | ルーティン・繰り返し・転記・通知 | 要約・文章作成・質問への回答 |
| つなぎ方 | 決まったトリガーとアクション | 会話の流れで動的に変わる |
| エラー時 | ログを見て原因を調べる | 返答の内容を人間が確認・修正 |
| ライセンス | Power Automateのライセンスが必要 | Microsoft 365 Copilotのライセンスが必要 |

どちらか一方を選ぶというよりも、「ルーティンはPower Automate、文章や判断のアシストはCopilot」という使い分けが実態としては多い。最初からどちらも導入しようとすると管理・教育のコストが増えるので、自分たちの一番の課題がどちらに対応しているかを先に決めてから始める方が現実的だ。

## 実際に詰まったポイント

展開する中でよく起きた問題を2点だけ書いておく。

**Power Automateのフローがいつの間にか止まっている**：作成者のアカウントが変わったタイミング（部署異動・退職）や、接続しているサービスのパスワードが変わったタイミングで止まることが多かった。サービスアカウントへの切り替えと、定期的なフローの稼働確認の仕組みを入れておくことで、発見が遅れるケースはかなり減った。

**Copilotに聞いたことを「そのまま使う」問題**：Copilotの返答をそのまま資料に貼り付ける事例が出てきた。Copilotの返答は参考にはなるが、事実確認・数字の確認は別途必要だという認識を使う人に持ってもらうための説明セットを作り、展開時に一緒に渡すようにした。

## この検証の限界

この記事は、特定の企業環境（大手企業・Microsoft 365 E5環境・製造・サービス業混在）での実際の展開経験をもとにしている。業種・規模・ライセンス構成によって状況は異なる可能性がある。

特に以下の点は環境依存が大きい：

- テナントのセキュリティポリシーがどこまで制限するか
- 外部システムのAPIがどこまで公開されているか
- IT部門のサポート体制がどの程度あるか

リリースノートや公式ドキュメントで確認した内容も含むが、自社の環境で検証せずにそのまま適用しないこと。特にセキュリティ設定に関わる変更は、事前に情報セキュリティ担当者と確認してから進めてほしい。
