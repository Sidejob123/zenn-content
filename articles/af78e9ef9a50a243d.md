Copilot Studio でエージェントを組んでいたとき、「この承認は自動でいいか、人間が確認すべきか」で迷う場面があった。自動にしたら間違ったデータが本番に流れた。人間が確認するフローにしたら、今度は担当者が承認を忘れて処理が止まった。

どちらも正解ではなかった。

その後、Power Automate・Copilot Studio・Claude Code を組み合わせて自動化を積み重ねる中で、「人間の承認をどこに残すか」について判断軸らしきものができてきた。整理してみる。

## 判断軸 1: 取り消せるかどうか

一番シンプルな判断基準はこれだ。

**取り消せる操作は自動化していい。取り消せない操作は人間が確認する。**

例えば、下書きを保存する・内部のデータベースに書き込む・ログに追記する——これらは後で消せる。間違えても直せる。これは自動でよい。

一方、外部に公開する・メールを送る・購入処理を走らせる・有料コンテンツを公開する——これらは取り消せない、または取り消すのに大きなコストがかかる。ここには人間の確認を残す。

Claude Code でブログの下書きを自動生成している。下書きの保存まではスクリプトが行い、公開ボタンは人間が押す設計にしている理由はここだ。「下書きを作ること」は取り消せる。「公開すること」は取り消せない（公開後に削除できても、検索インデックスや読者の記憶は残る）。

## 判断軸 2: 間違いを検知できるかどうか

自動化しても、間違いがすぐに分かるなら許容範囲が広がる。間違いが気づかれないまま積み重なる構造は危険だ。

Power Automate でSharePointのリストデータを別のシステムに転送するフローを組んでいる。転送自体は自動化している。ただし、転送後に件数と特定の集計値を照合するチェックを入れていて、ズレがあれば通知が来る設計にしている。

この場合、「転送」は自動でよい。「転送結果の確認」は人間が見る。承認フローと言うより、「出口の確認」を人間に残すイメージだ。

Copilot Studio で同じことをやるとき、エラーハンドリングの設計が甘いと「エラーが出たのに通知が飛ばず、気づかないまま次の処理が走る」という状況になる。エージェントに自律性を持たせるほど、この「検知できるか」が重要になる。

## 判断軸 3: 責任の所在が明確かどうか

これは技術的な話ではないが、実際の運用で一番効いてくる。

自動化した処理でミスが起きたとき、「誰が決定したか」が明確でないと対処が難しくなる。エージェントが自律的に判断してメールを送った場合、そのメールの内容に問題があったとき、誰が責任を持つのか。

大企業でこの問いに答えるのは難しい。そのため、「外部に何かを発信する操作」は、エージェントが文面を作っても、送信は人間が承認するフローにしていることが多い。

Claude Code でQiitaやZennへの記事投稿を自動化しているが、Threadへの返信は「案を生成してファイルに保存→人間が確認して承認→承認されたものだけ投稿」という2段階にしている。返信の内容は実在の個人とのやり取りになるため、自動投稿で問題が起きたときの責任の所在を明確にするためだ。

## 3つの判断軸をまとめると

| 判断軸 | 人間の承認が必要なケース |
|---|---|
| 取り消せるか | 取り消せない操作（公開・送信・購入） |
| 検知できるか | 間違いに気づけない・積み重なる構造 |
| 責任の所在 | 外部への発信・実在の個人とのやり取り |

この3軸が全部「人間確認が必要」を指す場合は、迷わず人間に委ねる。1つだけ当てはまる場合でも、「後で取り消せるか」が一番効きやすい判断軸だと感じている。

## Copilot Studio と Claude Code での具体的な使い分け

Copilot Studio は承認ステップをフロー内に組み込む機能がある。人間の承認をトリガーにして次の処理に進む設計が得意だ。ただし「承認忘れ」が起きると処理が止まるため、タイムアウトとエスカレーションの設計も必要になる。

Claude Code（`claude -p`）は、承認の概念を持たせるには外から設計する。「AIが生成した出力をファイルに保存→人間が確認→承認ファイルを作成→別のスクリプトが承認ファイルを見て次の処理を実行」という構造だ。手続きは増えるが、どこで人間が介在しているかが明示的になる。

## 整理して思ったこと

AIエージェントに自律性を持たせるほど、「どこを人間に残すか」を最初に設計しないと、後から差し込むことが難しくなる。

承認フローを後付けで追加しようとすると、既存の処理がそれを前提としていないため、設計を大きく変える必要が出てくる。Power Automate の承認フローを追加しようとして、フロー全体を作り直した経験が何度かある。

逆に言えば、最初から「取り消せない操作の前には確認を入れる」を設計原則として持っておくと、後からの改修コストが下がる。

自分の環境では今も、どこまで自動化するかの判断を試行錯誤している。正解はないが、上の3軸は「迷ったときの判断の手がかり」として機能している。
