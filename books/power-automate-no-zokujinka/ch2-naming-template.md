第1章で見たとおり、属人化の入り口は「名前」と「説明」が抜けているところにあります。この章では、追加費用なしで今日から始められる3つの対策を扱います。

1. 命名規則を決める
2. よく使う形をテンプレートにする
3. フローの外に、短い説明書を持つ

## 1. 命名規則を決める

### フロー名：一覧で見分けられることを最優先に

フロー名は、フローの一覧画面で並んだときに見分けられることが一番大事です。おすすめは、次の要素を決まった順番で並べる形です。

```
[部署やチーム]_[何をするか]_[対象や頻度]
```

例：

| 悪い例 | 良い例 |
|---|---|
| フロー 1 | 総務_備品申請_承認依頼 |
| テスト用（本番） | 営業_日次売上_集計メール |
| 新しいフロー | 経理_請求書受信_SharePoint保存 |

ポイントは3つです。

- **先頭に部署やチームを置く**：一覧を名前順に並べたときに、担当ごとにまとまる
- **「何をするか」を動詞まで書く**：「備品申請」だけでは、受け付けるのか、承認するのか、集計するのかが分からない
- **「テスト」「本番」は名前に入れない**：本番かどうかは名前ではなく、環境や状態で管理する（後述）。名前に入れると、テスト用がいつの間にか本番になったときに名前と実態がずれる

作成年月を名前に入れる方法もあります。ただ、修正のたびに名前を変えるわけではないので、「いつ作ったか」より「何をするか」が伝わることを優先したほうが、長く使えます。作成日や変更履歴は、後述の説明書に書きます。

### アクション名：既定の名前のまま残さない

フローの中のアクションは、追加した時点では「条件」「作成」「条件 2」「作成 3」といった既定の名前が付きます。これが一番、後から読む人を困らせます。

Microsoft Learnのコーディング ガイドラインでも、トリガーを「Trigger1」ではなく「新しいメールを受信」のように、目的や機能を表す名前にすることが推奨されています。

| 既定の名前 | 付け直した例 |
|---|---|
| 条件 | 金額が10万円以上か |
| 条件 2 | 申請者の部署が営業か |
| 作成 | 通知メールの本文を組み立て |
| 項目の取得 | 申請データをSharePointから取得 |

**条件の名前は「〜か」という問いの形にする**と、はい／いいえの分岐が読みやすくなります。

:::message alert
アクションの名前は、他のアクションから値を参照するときの式の中でも使われます。名前は、アクションを追加した直後、まだどこからも参照されていないうちに付けるのが一番確実です。後から変える場合は、そのアクションを参照している式が正しく動くかを、テスト実行で確認してください。
:::

### 変数名：種類が分かる接頭辞を付ける

変数は、名前を見ただけで「変数であること」と「何が入っているか」が分かるようにします。公式ガイドラインでも、種類ごとの接頭辞（例：変数に「Var_」）で分類することが紹介されています。

```
var_承認者メール
var_合計金額
var_エラー件数
```

camelCase（`varApproverEmail`）かアンダースコア（`var_approver_email`）かは、どちらでも構いません。**チームで1つに決めて、混ぜないこと**のほうが大事です。

### 命名規則は「A4半分」で十分

命名規則を決めるとき、最初から細かく作り込む必要はありません。むしろ、長いルールは読まれません。最初は、次の4項目をA4半分程度にまとめれば十分です。

1. フロー名の並び順（例：部署_何をするか_対象）
2. アクション名は既定のまま残さない（条件は「〜か」）
3. 変数の接頭辞（例：var_）
4. 「テスト」「本番」を名前に入れない

決めたルールは、公式ガイドラインが勧めるとおり文書にして、チームが見られる場所（SharePointのページなど）に置きます。

## 2. よく使う形をテンプレートにする

### ゼロから作らせない

承認フロー、通知フロー、データ集計フロー。社内で作られるフローの多くは、いくつかの決まった形に分けられます。

これを毎回ゼロから作ると、作る人ごとに、分岐の書き方やエラー処理の有無がばらばらになります。結果として、「このフローは、なぜこういう作りになっているのか」を毎回読み解く必要が出てきます。

よく使う形については、**社内向けの雛形フロー**を用意し、それを出発点にしてもらうと、品質のばらつきを大きく抑えられます。

### 雛形に最初から入れておくもの

雛形フローには、業務の中身ではなく、**誰が作っても必要になる部分**を入れておきます。

| 入れておくもの | 理由 |
|---|---|
| 命名済みのアクション | 既定の名前のまま広がるのを防ぐ |
| エラー時の処理（第6章） | 「エラー処理を入れ忘れる」を防ぐ |
| エラーの通知先を変数で1か所に | 通知先の変更を1か所で済ませる |
| 冒頭のメモ（目的・作成者・関連フロー） | 説明書への入り口を作る |

Power Automateには、Microsoftが用意したテンプレートもあります。ただ、社内の業務やルール（命名規則、通知先、エラー処理の方針）に合わせるなら、**社内で作った雛形を共有する**ほうが実態に合います。

### 雛形の配り方

雛形の配り方は、社内の環境によって選びます。

- **フローのコピー（名前を付けて保存）**：手軽。ただし、元の雛形を直しても、コピーした先には反映されない
- **ソリューションでまとめる**：Microsoft Learnによると、フローをソリューションに入れると、フローとその構成要素をある環境から別の環境に移しやすくなる。開発・テスト・本番のように環境を分けて運用する場合に向く（Dataverseが必要）

どちらの場合も、「雛形の最新版がどこにあるか」を命名規則と同じ場所に書いておきます。

## 3. フローの外に、短い説明書を持つ

### フローの中のメモだけでは足りない理由

アクションごとのメモは、「このアクションは何をしているか」を書くのに向いています。公式ガイドラインでも、複雑なフローや複数人で触るフローでは特に、アクションにメモを付けることが勧められています。

ただ、メモはフローを開かないと読めません。複数のフローが連携している場合、「全体として何をしているのか」「どのフローがどのフローを呼んでいるのか」は、個々のメモからは見えにくくなります。

### 説明書に書く4項目

そこで、フローの外に短い説明書を1つ持ちます。長い設計書は要りません。次の4項目を箇条書きにするだけで、引き継ぎのときの調査時間が大きく変わります。

```
■ フロー名：営業_日次売上_集計メール
■ 何のためのフローか：毎朝、前日の売上をまとめて営業部に送る
■ いつ動くか：毎日 8:00（日本時間）／繰り返しトリガー
■ 関連するもの：
  - 読むデータ：SharePointリスト「日次売上」
  - 送り先：営業部の配布リスト
  - 関連フロー：営業_売上入力_確認依頼
■ 注意事項：
  - 祝日も動く（祝日に止めたい場合は条件の追加が必要）
  - エラー時は 自動化担当の共有メールボックス に通知
■ 所有者：〇〇（主）、△△（副）
■ 変更履歴：2026-10 作成
```

置き場所は、チームの全員が見られる場所なら何でも構いません。SharePointのページ、Teamsのチャネルのタブ、Wikiなど、**命名規則と同じ場所**にまとめておくと探しやすくなります。

:::message
「繰り返し」トリガーで時刻を指定するときは、トリガーの設定にある「タイム ゾーン」を確認してください。Microsoft Learnの説明では、タイム ゾーン欄で、開始時刻をローカル時刻・協定世界時（UTC）・その他のタイムゾーンのどれで扱うかを選べます。説明書に「日本時間」と書いておくと、後から見た人が迷いません。
:::

## 3点セットに共通すること

命名規則、テンプレート、説明書。3つに共通しているのは、**「将来の自分か、別の誰かが開いたときに、意図が伝わるか」**という問いを、作るときに一度だけ持つことです。

フローは、動けばよいと考えて作ると、運用が始まった途端に負債になりやすいものです。反対に、作るときに数分だけ「読む人」のことを考えておけば、その数分が、半年後の何時間もの調査を省いてくれます。

## 今日やること

1. フロー名のルールを1行で決める（例：部署_何をするか_対象）
2. 一番よく使っているフローの、既定の名前のままのアクションを付け直す
3. そのフローの説明書を、4項目（目的・いつ動くか・関連するもの・注意事項）だけ書いてみる
