---
title: "第6章 「成功」なのに何もしていないフローを防ぐ"
---

フローの実行履歴に「成功」と表示されていると、私たちは安心します。ところが、「成功」が保証しているのは、**エラーが起きずに最後まで進んだこと**だけです。期待した仕事をしたかどうかまでは保証していません。

この章では、エラーにならないまま期待どおりに動いていない状態（本書では「無言の失敗」と呼びます）を、どう防ぎ、どう見つけるかを扱います。

## 「成功」なのに何もしていない典型例

| 例 | なぜ「成功」になるか |
|---|---|
| 取得したデータが0件で、ループが1回も回らなかった | 0件でもアクションとしては正常に終わる |
| 条件の判定がいつも「いいえ」側に入り、「いいえ」側に何も置いていなかった | 何もしない分岐を通っただけで、エラーではない |
| 途中のアクションが失敗したが、後続の設定で処理が続き、最後は成功扱いになった | 実行条件の設定によっては、フロー全体の結果が失敗にならない |
| 元データの更新前に動き、古いデータで処理した | データとしては正常に読めている |
| 送り先のリストが空で、誰にも送っていなかった | 送り先がない処理が、エラーにならない作りだった |

どれも、実行履歴を開くと「成功」の緑色が並んでいます。気づくのは、受け取るはずだった人からの「最近、届いていないけど？」という連絡です。

## 防ぎ方1：失敗を失敗として扱う（Try / Catch）

### スコープでまとめて、失敗したときの処理を作る

Microsoft Learnのコーディング ガイドライン「堅牢なエラー処理を採用する」では、関連するアクションをスコープにまとめ、try-catchのパターンでエラーを処理する方法が紹介されています。

```
[スコープ：Try（メインの処理）]
    ├ データの取得
    ├ 加工
    └ 送信
[スコープ：Catch（Tryが失敗したときだけ動く）]
    ├ どこで失敗したかを取り出す
    ├ 通知を送る（チームの共有先へ）
    └ 終了（状態：失敗）
```

Catchのスコープは、「実行条件の構成（実行後の設定）」で、**Tryが失敗した場合（必要に応じてタイムアウトした場合も）に実行**するように設定します。

### 最後に「失敗」として終わらせる

Catchで通知を送ったあと、そのままにしておくと、フロー全体の結果が「成功」になることがあります。そうなると、実行履歴の一覧では失敗に気づけません。

公式ガイダンスでも、エラーのためにフローを止める必要がある場合は**「終了」アクション**を追加し、状態を「失敗」に、理由をメッセージに設定するよう案内されています。Catchの最後に「終了（失敗）」を置いておけば、実行履歴にも失敗として残ります。

### 通知に入れる情報

通知を受け取った人が、すぐに動けるように、次の情報を入れます。

- フローの名前（`workflow()`関数で取れる情報の中の表示名）
- どのアクションで失敗したか、エラーメッセージ（`result()`関数でスコープ内の結果を取り出し、「配列のフィルター処理」で失敗したものだけに絞る方法が、公式ガイダンスで紹介されています）
- その実行を開くためのリンク（`workflow()`の情報から実行のURLを組み立てる例が、公式ガイダンスに載っています）
- 説明書（第2章）の場所

:::message
公式ガイダンスは、ログや通知を増やしすぎると、アクション数が増えてフローの性能に影響したり、通知が多すぎて誰も見なくなったりする点にも注意を促しています。通知は「人が動く必要があるとき」に絞りましょう。
:::

### 一時的な失敗は、再試行に任せる

ネットワークや相手のサービスの一時的な不調による失敗は、すぐに人に知らせるより、まず再試行させたほうがよい場合があります。アクションの設定で**再試行ポリシー**を指定でき、公式ガイダンスでは、間隔を徐々に延ばしていく指数関数的な再試行が推奨されています。

## 防ぎ方2：「何もしなかった」を失敗として扱う

Try / Catchで捕まえられるのは、エラーになった失敗だけです。「0件だった」「何も送らなかった」は、エラーではないので、Catchには入りません。そこで、**想定外に何もしなかった場合を、自分で失敗にする**作りを足します。

### 件数を確かめる

データを取得したあとに、件数を確かめる条件を置きます。

```
[データの取得]
[条件：取得した件数が0件か]
    はい → 本当に0件があり得る業務か？
            あり得ない → 終了（失敗：「データが0件でした。取得元を確認してください」）
            あり得る   → 「本日は0件でした」と明記して通知
    いいえ → 通常の処理へ
```

ポイントは、**「0件」と「取得に失敗した」を、受け取る人が区別できるようにする**ことです。

### 条件分岐の「何もしない側」にも、一言残す

条件の「いいえ」側を空にしておくと、どちらを通ったのかが実行履歴を細かく見ないと分かりません。何もしない側にも、「作成」アクションなどで「対象外のため処理なし」と残しておくと、あとから実行履歴を見たときに意図が分かります。

### 送り先が空でないかを確かめる

送り先を表やグループから取ってくる作りの場合、送る前に「送り先が1件以上あるか」を確かめます。空なら、送らずに失敗として知らせます。

## 防ぎ方3：結果の側から確かめる

ここまでは、フローの中で失敗を見つける方法でした。もう1つ有効なのが、**フローの外から、結果を確かめる**方法です。

- 毎日送られるはずのメールが、今日届いたか
- 毎日増えるはずのリストの行が、今日増えたか
- 更新されるはずのファイルの更新日時が、今日になっているか

これらを、別の小さなフローで毎日確かめ、期待どおりでなければ知らせます。処理をするフローとは別の経路で確かめるので、処理をするフローが「成功」と言っていても、実際には何も起きていないことに気づけます。

:::message alert
「結果の側から確かめる」フロー自体が止まっていては意味がありません。このフローは、何もなくても「今日も確認しました」と週に1回程度知らせるようにしておくと、確認役が止まっていることにも気づけます。
:::

## 所有者へのメール アラートも生かす

Microsoft Learnのエラー処理のガイダンスによると、Power Automateは、接続の切断などの一般的な障害や重大な障害について、フローの所有者にメール アラートを送ります。共同所有者にチームのグループを入れておく（第4章）と、この知らせを受け取れる人が増えます。

より本格的に監視したい場合は、Application Insightsを使ってクラウドフローのエラーのアラートを受け取る方法も、公式ガイダンスで紹介されています。

## この章のまとめ

- 「成功」は、エラーが起きなかったことしか意味しない
- スコープでTry / Catchを作り、最後は「終了（失敗）」で失敗として残す
- 0件・空の送り先など「何もしなかった」を、自分で失敗にする
- 処理とは別の経路で、結果を確かめる

## 今日やること

1. 一番大事なフローに、Try / Catchのスコープと「終了（失敗）」を入れる
2. データを取得した直後に、件数の確認を1つ入れる
3. 毎日届くはずのものが届いたかを確かめる方法を、1つ決める
