Power Automateは、標準のコネクタだけでなく、HTTPアクションなどを使って社内外のAPIともつなげます。最近は、生成AI（Azure OpenAIなど）を呼び出して、問い合わせの分類や文章の要約をフローに組み込む相談も増えています。

この章では、外部とつなぐフローを「動く」から「安定して動き続ける」にするための設計を扱います。

:::message
HTTPアクションはプレミアム コネクタです。利用には対応するライセンスが必要です。社内で使ってよいかどうかも含めて、事前に管理者に確認してください。
:::

## 認証の選び方

### 選べる認証の種類

HTTPアクションでは、呼び出す相手に合わせて認証の種類を選びます。主なものは次のとおりです（画面の名称や選べる種類は、環境や更新によって変わることがあります）。

| 認証の種類 | 概要 | 注意点 |
|---|---|---|
| なし | 認証の要らない公開API | 社内の情報を送る先には使わない |
| 基本認証 | ユーザー名とパスワード | 資格情報の管理と、組織のアクセス制御の影響を受けやすい |
| Microsoft Entra ID（旧Azure AD）OAuth | アプリ登録のクライアントIDと、シークレットまたは証明書 | シークレットに有効期限がある |
| クライアント証明書 | 証明書で認証 | 証明書にも有効期限がある |
| マネージド ID | Azureのリソースに割り当てたIDで認証 | 使える場面や設定に条件がある。管理者の協力が必要なことが多い |

### 最初に確かめる質問

どれを選ぶかを考えるときは、まず次の2つを確かめます。

1. **呼び出す相手は、Microsoft Entra IDで認証できるか**（社内のAPIや、Azureのサービスか）
2. **組織として、どの認証方式を許可しているか**（セキュリティ部門・IT部門のルール）

1が「はい」なら、Entra IDのアプリ登録を使うOAuthか、条件が合えばマネージド IDが候補になります。どちらを使うかは、組織のルールと管理者の権限によって決まります。フローの作り手だけでは決められないことが多いので、早めに相談しておきます。

## 「テストでは通るのに、本番で弾かれる」

外部とつなぐフローで多い困りごとが、「テストでは通ったのに、本番の実行で401や403が返る」というものです。切り分けの順番は次のとおりです。

1. **実行履歴で、HTTPのステータスコードとエラーメッセージを確認する**
2. **401なら認証の問題、403なら権限の問題**と考える（認証は通っているが、その操作の権限がない）
3. 401の場合
   - シークレットや証明書の**有効期限**が切れていないか
   - 組織の**条件付きアクセス**（接続元の場所や端末による制限）の影響を受けていないか。クラウドフローは組織のネットワークの外から実行されるため、社内からのテストと条件が変わることがあります
4. 403の場合
   - アプリ登録や、相手側のシステムで、必要な権限が与えられているか

### 有効期限は「止まる日」が決まっているということ

Entra IDのアプリ登録で作るクライアント シークレットには、有効期限があります。期限が切れた瞬間に、フローは認証エラーで止まります。言い換えれば、**止まる日が前もって分かっている**ということです。

- シークレットを作ったら、期限の日付を説明書（第2章）に書く
- 期限の1か月前に、更新の予定を入れる（担当者の予定表、チームの予定表）
- 更新の手順（どこで新しいシークレットを作り、どこに入れ替えるか）も説明書に書く

## 生成AIをフローに組み込むときの設計

### 出力の形を決め、必ず確かめる

生成AIの出力を、そのまま次の処理に流すのは危険です。想定と違う形で返ってきたとき、後続の処理が誤動作します。

- **出力はJSONなど、決まった形で返すよう指示する**：プロンプトに、返してほしい形の例を入れておく
- **受け取ったら、形を確かめる**：「JSONの解析」で読めるか、必要な項目がそろっているか、値が想定の範囲かを確かめる
- **確かめに通らなければ、自動で進めずに人に回す**

```
[生成AIを呼び出す]
[出力の形を確かめる]
    ├ 正しい形 → 後続の自動処理へ
    └ 想定外   → 自動処理を止め、担当者に確認を依頼
```

### 再試行は、失敗の種類で分ける

| 失敗の種類 | 考え方 |
|---|---|
| 429（要求が多すぎる） | 少し待ってから再試行する。応答に待ち時間の指定があれば、それに従う |
| 500番台（相手側の一時的な不調） | 間隔を延ばしながら数回再試行する |
| 401・403（認証・権限） | 再試行しても直らない。すぐに人に知らせる |

アクションの再試行ポリシー（第6章）は便利ですが、直らない種類の失敗まで繰り返すと、知らせが遅れるだけです。

### 記録を残す

生成AIを使うフローでは、少なくとも次の4つを記録しておくと、うまくいかなかったときに原因を切り分けられます。

- 入力（何を渡したか）
- 出力（何が返ってきたか）
- 出力をどう判断したか（分類の結果、確信度など）
- 実際にどう処理したか（どこに振り分けたか）

入力に個人情報や機密情報が含まれる場合は、記録の置き場所と保存期間を、組織のルールに合わせて決めます。

### 費用と、想定外の入力に備える

- **呼び出し回数の上限を決める**：テスト中にループの設定を誤ると、気づかないうちに大量の呼び出しが起きることがあります。1日の呼び出し回数を記録し、想定を超えたら知らせる仕組みを先に作っておきます
- **外から届く文章をそのまま渡す場合は、指示文の紛れ込みを想定する**：問い合わせメールなどの本文に、AIへの指示のような文章が含まれている可能性があります。完全に防ぐのは難しいため、「確信度が低いとき」「いつもと違うパターンのとき」は自動で進めずに人が確認する、という安全策を入れておきます

### 精度は、運用しながら確かめる

生成AIの判断の精度は、入力の傾向が変わると下がることがあります。月に1回など、処理した結果から一部を抜き出して人が確かめ、誤りが一定の割合を超えたらプロンプトを見直す、というルールを最初に決めておくと、確認が形だけになりにくくなります。

## 今日やること

1. 外部とつなぐフローで使っているシークレット・証明書の有効期限を調べ、説明書に書く
2. 生成AIの出力を、確かめずに次の処理へ流している箇所がないかを確認する
3. 再試行の設定が、直らない失敗（401・403）まで繰り返していないかを確認する
