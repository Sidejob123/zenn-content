---
title: "付録 コピーして使える設計チェックリスト"
---

本書の内容を、フローを作るとき・本番に出すとき・引き継ぐときのチェックリストにまとめました。社内のレビューや、自分のフローの見直しに、そのままコピーして使ってください。

:::message
すべての項目を満たす必要はありません。止まったときの影響が大きいフローほど、多くの項目を満たすようにしてください。
:::

## A. 作る前（第3章）

```
□ 送る前に人の確認が必要かを決めた
□ データが取れなかったときの動き（止める／「取得失敗」と送る）を決めた
□ エラーを知らせる先を、個人ではなくチームの共有先にした
□ 元のデータが何時に確定するかを確認し、それより後に動く時刻にした
□ 「繰り返し」トリガーのタイム ゾーンを確認した
□ 最初の版で自動化する範囲を、最小限に絞った
□ データの置き場所（SharePointリスト／Excel）と、データの形を決めた
```

## B. 作るとき（第2章）

```
□ フロー名がルール（例：部署_何をするか_対象）に沿っている
□ フロー名に「テスト」「本番」を入れていない
□ 既定の名前のまま残っているアクションがない（条件は「〜か」の形）
□ 変数に、決めた接頭辞（例：var_）が付いている
□ 複雑な部分のアクションに、メモで説明を付けた
□ 入れ子が深くなりすぎていない（スイッチ・子フロー・早めの除外を検討した）
□ 承認者・送り先・しきい値をフローに直接書かず、設定表から読んでいる
□ 環境ごとに変わる値を、環境変数にした（ソリューションを使う場合）
```

## C. 失敗への備え（第6章）

```
□ メインの処理をTryのスコープにまとめた
□ Tryが失敗（とタイムアウト）したときに動くCatchのスコープを作った
□ Catchの通知に、フロー名・失敗したアクション・エラー内容・実行へのリンクを入れた
□ Catchの最後に「終了（失敗）」を置いた
□ 一時的な失敗に、再試行ポリシーを設定した
□ 取得したデータの件数を確かめ、想定外の0件を失敗として扱っている
□ 送り先が空でないかを確かめている
□ 処理とは別の経路で、結果（届いたか・増えたか）を確かめる方法がある
```

## D. 承認フロー（第5章）

```
□ 承認の種類（全員／最初に応答／カスタム／順次）を、意味を確認して選んだ
□ 承認依頼の本文に、その場で判断できる情報（誰が・何を・いつまでに・金額など）を入れた
□ 承認者が実際に使う端末（スマートフォンを含む）で、表示と応答を確かめた
□ 承認者を、承認者の表から読んでいる
□ 承認のアクションにタイムアウトを設定し、期限切れのときの処理を作った
□ エスカレーションの先に、回ってきた理由を添えている
□ 承認の結果（いつ・誰が・何を・理由）をフローの外に記録している
```

## E. 外部とつなぐとき（第7章）

```
□ 認証の種類を、組織のルールに沿って選んだ
□ シークレット・証明書の有効期限を説明書に書き、更新の予定を入れた
□ 401と403を区別して切り分けられるよう、通知にステータスコードを入れている
□ 生成AIの出力を、決まった形で返させ、受け取ったあとに確かめている
□ 確かめに通らないときは、自動で進めずに人に回している
□ 再試行を、失敗の種類（429・500番台・401/403）で分けている
□ 入力・出力・判断・処理の記録を、組織のルールに合った場所に残している
□ 呼び出し回数を記録し、想定を超えたら知らせる仕組みがある
```

## F. 本番に出す前

```
□ 共同所有者（後任候補またはチームのグループ）を追加した
□ 説明書（目的・いつ動くか・関連するもの・注意事項・所有者・変更履歴）を書いた
□ 説明書と命名規則を、チームが見られる場所に置いた
□ 想定した時刻・条件で動くことを、テスト実行で確かめた
□ わざと失敗させて、Catchの通知が届くことを確かめた
□ 年に数回しか動かないフローなら、次に動く時期を説明書に書いた
```

## G. 棚卸しと引き継ぎ（第8章）

```
□ 担当フローの一覧（名前・目的・所有者・最後に動いた日・状態・影響・説明書）がある
□ 止まったときの影響が大きい順に、整える優先順位を決めた
□ 使われていないフローを、担当者に確認したうえでオフにした
□ 引き継ぎでは、最初に後任者を共同所有者に追加した
□ 後任者がフローを開けることを確かめてから、接続を切り替えた
□ 有効期限のあるものと、たまにしか動かないフローの情報を渡した
□ 四半期に1回、棚卸しの表を更新する予定を入れた
```
